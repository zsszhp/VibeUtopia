## 1. 执行摘要

前端是一个**单路由、三栏工作台**形态的内容风控控制台。视觉完成度较高，但工程底座存在**系统性欠账**：类型检查当前是失败的、V3 API 层整条链路不可达、多个核心数据映射错位、约 22% 的组件是从未被引用的死代码。

| 维度 | 评分 | 一句话判断 |
|------|------|-----------|
| 构建与类型安全 | ★★☆☆☆ | `vue-tsc` 当前 6 个错误，`npm run build` 必失败；`any` 共 76 处 |
| API 层与契约 | ★☆☆☆☆ | V3 路由前缀双重拼接，前端 `v3Api` 全部 404；无 OpenAPI 生成 |
| 状态管理 | ★★★☆☆ | Pinia setup 风格规范，但错误态无 UI 消费、设置项无消费者 |
| 组件工程 | ★★☆☆☆ | 5 个死组件（1443 行）；最大文件 1033 行；ECharts 样板 5 处重复 |
| 性能工程 | ★★☆☆☆ | echarts chunk 1.1MB；无虚拟列表/懒加载/ResizeObserver；无性能预算 |
| 可测试性 | ★☆☆☆☆ | 前端测试数量 = 0；组件强依赖全局 store，无注入点 |
| 可维护性 | ★★☆☆☆ | 456 处硬编码色值、0 个 CSS 变量；平台名映射 3 份拷贝 |
| 工程规范 | ★☆☆☆☆ | 双 lockfile；无 i18n；无 a11y；console.log 入生产 |

**最严重的 5 个问题（P0）：**

1. **V3 API 整层 404**：`routes_v3.py:48` 的 `APIRouter()` 无 prefix，但装饰器路径已含 `/api/v3/...`（如 `routes_v3.py:867`），而 `main.py:59` 又 `include_router(router_v3, prefix="/api/v3")`，实际注册路径为 `/api/v3/api/v3/counterfactual/simulate`，前端 `api/index.ts:4,259` 请求 `/api/v3/counterfactual/simulate` 必 404。
2. **反事实仿真传参错误**：`RightPanel.vue:200` 把 `reviewStore.currentTaskId`（任务 ID）当 `text` 传给 `CounterfactualPanel`，而 `CounterfactualPanel.vue:151` 期望的是**原始文案**。
3. **平台名称映射三份拷贝且键名不一致**：`LeftPanel.vue:211-215` 用中文名查 `platform_reactions`，后端返回英文键（`platforms/bilibili.py:7` 等），热力图永远全 0。
4. **进度单位错位**：store 的 `progressPercent` 已是 0–100（`stores/index.ts:110`），`Workbench.vue:6` 原样传入，`AnalysisDashboard.vue:38` 再 `* 100`，完成后显示 **10000%**。
5. **类型检查失败导致构建阻断**：`vue-tsc` 6 处错误（KnowledgeGraph×2、PropagationGraph、SignalPanel、EntityRiskTimeline、BloggerProfile），`package.json:8` 的 `vue-tsc -b && vite build` 无法通过。

**总体判断**：前端处于「视觉先行、工程滞后」状态。当前首要任务不是加功能，而是**恢复构建绿灯 + 修复契约断链 + 清偿死代码**，否则任何新功能都会叠加在流沙上。

## 4. 状态与 API 层评估

### 4.1 Pinia Store

`stores/index.ts` 三个 store（review/history/models）采用 setup 风格，结构清晰，`reset/clearError` 齐全，历史详情有 `detailCache`（`stores/index.ts:212-239`）——这部分是合格的。

问题：

1. **错误态零消费**：`stores/index.ts:63-71` 维护 `error/errorTimestamp`，但全前端无任何组件读取 `reviewStore.error`（02 审计已指出，工程侧同样成立）——错误处理链在 store 层断裂。
2. **WS 消息未类型化**：`stores/index.ts:120` `handleWsMessage(data: any)` 的 5 个 case 全靠运行时字段猜测。
3. **进度单位双标**：`stores/index.ts:110` 赋值为 `progress * 100`（0–100），而 `AnalysisDashboard` 的 props 契约按 0–1 设计（`AnalysisDashboard.vue:38`），两端未统一。
4. **设置无消费者**：`SettingsDialog.vue:88-117` 把 `apiBase/defaultDepth/theme/model` 写入 localStorage，但 `api/index.ts:3-4` 硬编码 base、`App.vue:105` 硬编码暗色、`LeftPanel.vue:136` 硬编码 `standard`——**4 项设置 0 项生效**。

### 4.2 API 层

`api/index.ts` 是**扁平函数集合**，没有 axios 实例，意味着：无 baseURL 统一管理、无请求/响应拦截器、无超时、无统一错误归一、无取消令牌、无重试。`stores` 与组件各自解析 `e?.response?.data?.detail`。

分层现状：

| 层 | api/*.ts | v3Api | bloggerApi |
|----|----------|-------|------------|
| 请求类型 | ✅ 有 interface | ⚠️ 部分 inline | ❌ 全 inline |
| 响应类型 | ✅ 泛型标注 | ❌ 无 | ❌ 无 |
| 运行时校验 | ❌ 无（无 zod） | ❌ | ❌ |

`UploadResponse`（`api/index.ts:167-171`）等响应契约是手写 TS interface，**无 OpenAPI/JSON Schema 对齐机制**——后端 `routes.py` 的 Pydantic model 与前端 interface 靠人肉同步，已发生漂移（见 §7）。

## 5. 性能与体验工程

### 5.1 加载与产物

| 产物 | 字节数 | 说明 |
|------|--------|------|
| `echarts-*.js` | 1,119,316 | 单 chunk 超 1MB；未按需注册（未用 `echarts/core` + 模块化引入） |

| CSS 合计 | ~42KB | |

JS 合计约 **1.67MB**（未压缩）。缺：路由级/组件级 `defineAsyncComponent`（除 Workbench 路由懒加载外全同步）、echarts 按需、d3 子路径导入（`d3-force`/`d3-selection` 等）、CSS 产物分析、性能预算（performance budget）与 CI 门禁。

`vite.config.ts:31` 把 `chunkSizeWarningLimit` 提到 800 是**掩盖告警**而非治理。

### 5.2 长任务与实时更新

做得好的部分：

- WebSocket 断线自动降级 3s 轮询（`WebSocketManager.vue:40-76`），恢复后停轮询
- 帧级进度、序列描述、风险预警流（`stores/index.ts:136-163`）
- 底部全局进度条（`App.vue:41-47`）

缺陷：

1. 重连是**固定 5s**（`WebSocketManager.vue:79-87`），无指数退避、无心跳 ping/pong、无重连次数上限。
2. `WebSocketManager.vue:25,41` 残留 `console.log`（项目规范禁止生产 console.log）。
3. **上传无失败恢复**：`LeftPanel.vue:162-181` 串行 for-await，任一文件失败整个 `handleSubmit`（`LeftPanel.vue:183-200`）无 catch，产生 unhandled rejection；无断点续传/分片。后端 `routes_resume.py` 已有续传路由（`main.py:71` 注册 `/api/v1`），但**前端未接**。
4. 后端单文件上限 100MB（`routes.py:650`），大视频单请求超时风险高，前端无超时配置。

### 5.3 重渲染与大列表

- `PolarizationChart.vue:152`、`DimensionRadar.vue:46`、`PropagationGraph.vue:177` 均 `watch(..., { deep: true })` 全量重渲染，传播图每次**重建整个 forceSimulation**（`PropagationGraph.vue:49-72`），节点动画从头跑。
- 预警流 `AnalysisDashboard.vue:206-227` 用 `TransitionGroup` 渲染 `riskAlerts` 全量数组，**无虚拟滚动、无上限截断**——长任务下预警可达数百条。
- 无 `v-memo`/`shallowRef`/防抖；帧进度图片 URL 每帧变更触发 reflow。

## 7. 与后端契约问题

## 8. 行业工程实践对标

| 实践 | 行业标准 | 本项目 | 差距 |
|------|----------|--------|------|
| **API 契约** | OpenAPI → 前端类型代码生成，CI 校验漂移 | 手写 interface + 无响应类型 | P0：契约全靠人肉 |

### 10.2 新功能工程规范（防止再欠账）

1. **契约优先**：新增接口先加 Pydantic model → 重生成 `types/api.d.ts` → 前端引用生成类型，禁止再手写 `any`/`Record<string, any>`。
2. **组件红线**：单文件 ≤300 行；props/emits 必须有 TS 接口；业务阈值进 `config/` 或 store，禁止写在 template 表达式。
3. **图表规范**：一律走 `useECharts`/`useD3Force` composable；禁止组件内裸 `echarts.init`。
4. **状态规范**：异步 action 必须 `loading/error/data` 三态齐全，且 error 必须有 UI 出口。
5. **样式规范**：只用设计令牌变量与语义 class；新色值必须先入 `tokens.css`；Tailwind 要么全面采用要么移除，禁止三套并存。
6. **CI 门禁**：`vue-tsc` 0 错误、`vitest` 通过、bundle size 预算（echarts chunk <300KB gzip、首屏 JS <200KB gzip）、无 `console.log`（eslint no-console）、无新增 `any`（eslint no-explicit-any）。
7. **上传/长任务**：所有长流程必须有进度、失败重试、断点续传；WebSocket 必须有 fallback 轮询（现有 `WebSocketManager` 模式可复用）。
