# 多模态视频理解审计

> **文档定位**：调研审计｜抽帧/OCR/音频链路覆盖率与漏检风险
> **所属目录**：`docs/05_调研审计/`


- 审计对象：`src/backend/services/` 下视频/音频/OCR/跨模态/细粒度全部模块
- 对照文档：`docs/02_系统设计/08_多模态风控.md`、`docs/02_系统设计/13_细粒度视频理解.md`、`docs/07_研究与参考/03_07_研究与参考/03_技术白皮书.md`
- 审计方法：逐文件精读源码 + 管线接线追踪 + 测试/评测资产盘点 + 行业学术检索（anysearch）
- 结论口径：以**代码真实行为**为准，文档宣称与实现不一致处逐条标注

## 1. 执行摘要

多模态视频理解的**骨架是完整的**：本地视频 → 关键帧提取 → OCR/画面理解 → 音频转写 → 跨模态冲突 → 细粒度专项检测（地图/代码/符号/时序）→ 风险分融合，模块划分与设计文档基本对应。但逐环节核对后，**"宣称能力"与"真实能力"之间存在系统性落差**，且有 5 个 P0 级缺陷直接使部分能力整体失效：

1. **V3.5 帧序列建模整条链路失效**：`frame_sequence_analyzer.py:246` 读取 `delta_result.frames`，而 `DeltaFrameResult` 只有 `extracted_frames`（`delta_frame_extractor.py:83-88`），导致序列描述/因果链/动作事件/视频-文案冲突检测永远拿到空列表，静默返回"无可用帧数据"。
2. **基础版跨模态冲突是空转**：`analyzer.py:380-383` 调用 `detect_conflicts` 时 `visual_description=None, audio_transcript=None`，模态计数=1，恒返回"单模态内容，无需跨模态检测"。
3. **区域放大"细审"只放大不识别**：`region_amplifier.py` 裁剪出 448 patch 并拼好 prompt，但**从未把 patch 送入 VLM/OCR**（`analyze_frame` 结束于 `RegionDetail(...analysis_prompt=prompt)`，`ocr_text` 恒为空），小区域文字识别（文件夹名等）无闭环。
4. **地图审核的"地理知识库"未使用**：`map_auditor.py:59-95` 定义了经纬度范围，实际只做 OCR 文字关键词匹配（`_check_keywords`，`map_auditor.py:282-296`）——地图上没印"台湾"二字就判缺失，误报方向与漏报方向同时存在。
5. **失败即安全（fail-open）的漏报偏置**：VLM/JSON 解析失败时各检测器一律返回 `risk_level="safe"`（`frame_risk.py:401-405`、`map_auditor.py:154-161`、`symbol_detector.py:105-111`、`code_tracer.py:163-169`），与风控产品"失败应升警"的直觉相反。

此外：`frame_risk.py` 的画面风险评估器**未被任何管线调用**（孤儿模块）；Paraformer 转写 `_parse_result` 注释明言"实际应该下载 result_url …这里简化处理"（`audio_transcriber.py:167-169`）；全部模块无单元测试，无金标准数据集，设计文档中的 85%/90% 等指标**零实测支撑**；`tests/video/` 四案例只有原始媒体、没有标注、没有跑批脚本。

**总体判断**：管线骨架 ~70% 落地，宣称的"几帧定生死"细粒度能力目前真实有效性约 **30-40%**（地图 VLM 直判部分可用，代码溯源依赖 30 项硬编码词典，闪帧/小字场景基本不可用），距离设计验收标准（短暂画面检出率≥85%、地图召回≥90%）有明确差距，需先修 P0 再谈指标。

### 2.4 跨平台/Windows 观察

- 路径处理统一用 `os.path`/`pathlib`，中文路径（`tests/video/*_音频.mp3`）匹配规则特判了"音频"后缀（`video_extractor.py:122-134`），Windows 下可工作。
- 依赖 `ffmpeg`/`ffprobe` 可执行文件在 PATH（`keyframe_extractor.py:222-251`）；未打包 ffmpeg 的 Windows 环境三条视频路径全部失败。
- 临时目录 `tempfile.mkdtemp` 在 keyframe/dense/delta/audio 四处创建后**从不清理**（如 `keyframe_extractor.py:111`、`dense_frame_scanner.py:109`、`delta_frame_extractor.py:145`、`audio_analyzer.py:190`），长视频多任务下磁盘泄漏。
- `asyncio.get_event_loop()` + `run_in_executor` 为旧式写法（`keyframe_extractor.py:257` 等），Windows Proactor 事件循环下可用但已属废弃路径。
- OpenCV `cap.set(CAP_PROP_POS_FRAMES)` 随机seek在部分 Windows/编码组合下不精确（`keyframe_extractor.py:295`），场景中帧可能偏移。

## 3. 各子模块能力评估（真实 vs 宣称）

### 3.1 video_extractor.py（143 行）
- **真实**：仅本地文件；OCR 文本+音频转写合并；优先复用同目录 mp3（4 级匹配规则）。✅ 与设计"仅本地视频"一致。
- **缺口**：`subtitles`/`description` 恒为空；无失败分级，OCR/音频双失败时退化为文件名文本（`video_extractor.py:85-90`），下游文本风控在"只有标题"上运行但不被告知置信度降级。
- **细节风险**：`_find_existing_audio` 规则 4"目录下任意 mp3"（`video_extractor.py:136-141`）在多视频目录可能取错音频，造成**音画错配**进入风控。

### 3.2 keyframe_extractor.py（579 行）
- **真实**：PySceneDetect ContentDetector（阈值 27）→ ffmpeg 固定间隔（默认 **5 秒**，`keyframe_extractor.py:76`）→ OpenCV 兜底；pHash 去重（阈值 8）；上限 50 帧。
- **与设计偏差**：
  - 设计说"场景切换后第一帧"，实现取**场景中间帧**（`keyframe_extractor.py:284-287`）；
  - 设计说 30s 间隔，实现 5s（反而更密，但与文档不一致）；
  - 设计中的 face_detection / text_detection 策略**未实现**；
  - 超 50 帧时**均匀采样裁剪**（`keyframe_extractor.py:168-173`）——恰恰丢掉低频高危场景，与"覆盖关键画面"目标相反；
  - 输出固定缩放到 **640x360**（`keyframe_extractor.py:79-80,463-469`），这是后续"小区域识别率≥80%"宣称的**根因性障碍**。
- **其他**：pHash 为 8x8 简化版（`keyframe_extractor.py:471-483`），对渐变/字幕切换不敏感；`_load_extracted_frames` 从文件名解析时间戳（`keyframe_extractor.py:536-544`），ffmpeg 路径产出的 `frame_%04d.jpg` **解析不到时间戳（恒 0.0）**，证据帧时间轴会失真。

### 3.3 frame_ocr.py（255 行）
- **真实**：唯一路径 `call_vlm` 提示词 OCR（`frame_ocr.py:130-164`），JSON 解析，置信度硬编码 0.85，帧间全文去重，并发信号量 3。
- **与设计偏差**：设计的 GLM-OCR 本地 0.9B/94.62%、bbox 坐标、文字类型分类（字幕/水印/贴图）均未实现；无 bbox 输出（`OCRItem.bbox` 恒空）；`get_ocr_status` 恒返回 `api_ocr: True`（`frame_ocr.py:250-255`）——状态 API 说谎。

### 3.4 frame_risk.py（461 行）— **孤儿模块**
- 全仓检索无任何调用方（仅自身定义）。`models.py:320-321` 有 `frame_risk_level` 字段但无人写入。
- 若被调用：VLM 路由→直连 Qwen-VL/GLM-4V 降级→规则降级；JSON 解析失败返回 `risk_level="safe", summary="解析失败"`（`frame_risk.py:401-405`）——**解析失败当作无风险**，漏报偏置。
- 规则降级用文件大小>500KB 判 low（`frame_risk.py:445-452`），无信息量。
- `_call_direct_vision` 先检查 `DEEPSEEK_API_KEY` 是否配置（`frame_risk.py:304-308`）再调 Qwen/GLM——门控条件与实际使用凭据不一致。

### 3.5 audio_transcriber.py（250 行）
- **真实**：Paraformer 异步任务（上传→建任务→轮询≤10min→删临时文件），支持说话人分离。
- **缺陷**：`_parse_result` 注释自认"实际应该下载 result_url 的内容，这里简化处理"（`audio_transcriber.py:167-169`）——按 DashScope 真实 API 行为，结果在 `result_url`，`data.sentences` 通常不存在，**转写文本大概率为空**；`routes.py:191-193` 直接传视频文件路径而非音频轨。
- 与 `audio_analyzer` 的 whisper 路径**重复转写**同一视频（routes 先 whisper 合并文案、再 Paraformer 追加），成本×2。

### 3.6 audio_analyzer.py（375 行）
- **真实**：ffmpeg 抽 16k 单声道 WAV → faster-whisper（vad_filter）→ openai-whisper 降级；LLM 文本情感（非 SER 声学模型）。
- **与设计偏差**：默认 `whisper_model="base", device="cpu", int8`（`audio_analyzer.py:84-86`）——设计承诺的 large-v3+GPU 路线完全未配置化接线；`video_config.yaml` 的 `audio:` 段**未传入** `AudioAnalyzer()`（`video_extractor.py:71` 无参构造）。
- 情感分析失败静默降级 neutral/0.3 置信（`audio_analyzer.py:325-333`），下游无法区分"真中性"与"分析失败"。

### 3.7 cross_modal_detector.py（340 行）+ transcript_detector.py（263 行）
- 跨模态：单次 LLM 调用，三模态文本各截 1000 字（`cross_modal_detector.py:88-92`），规则兜底仅 7 个敏感词（`cross_modal_detector.py:144-155`）；`integrate_cross_modal_score` 隐藏风险 +15、冲突>50 +10。
- **致命接线问题**：`analyzer.py:378-384` 传 `visual_description=None, audio_transcript=None` → 恒判定单模态直接返回，**主分析器里的"跨模态冲突检测"步骤是仪式性的**。
- transcript_detector：规则预筛（无标点长句/叠字/碎句）+ LLM 复核，用于把 ASR 乱码句排除出改写。硬编码乱码词表（"忽来忧/踢击/屁眼上面"等，`transcript_detector.py:86-90`）明显过拟合单一案例；且"含敏感词的乱码句"可能被整句丢弃，存在风险句漏改写。

### 3.8 multimodal_analyzer.py（486 行）
- `analyze_visual/analyze_audio/analyze_ocr` 本质是 **LLM 对文本描述做风险打分**，不是视觉分析——`analyze_visual` 接收的是 `visual_description` 字符串（`multimodal_analyzer.py:101-120`）。设计文档的"画面内容审核六类风险"实际由（未接线的）frame_risk 承担。
- `VideoSegmentAnalyzer.generate_visual_description_batch` 为控成本最多 5 帧（`multimodal_analyzer.py:398`），供知识图谱用（`blogger_video_indexer.py:22`）。
- 融合权重 `max(text, visual×0.8, audio×0.7, ocr×0.6)` + 双高风险 +10（`multimodal_analyzer.py:285-302`）为拍脑袋系数，无标定依据。

## 4. 性能/成本/可靠性

### 4.1 VLM 调用量（10 分钟视频、细粒度全开、估算）

|------|------|------|

| 敏感符号 | ≤50 VLM | 串行 |
| 时序异常 | 每异常段 1 VLM | |
| 帧序列（当前空转） | 若修复：ceil(帧数/6) VLM + 2-3 LLM | |
| 跨模态 | 1-2 LLM | |

保守估计 200-350 次视觉调用，按 Qwen-VL-Plus 单次 1-3 秒 + 单次 ¥0.01-0.05 计，**单视频成本 ¥2-15、墙钟 10-30 分钟**，远超设计"≤30 秒/10 分钟视频、≤¥2/视频"（`30_细粒度视频理解设计.md:892-893`）。`resumable_analyzer.py:447` 估算 `_llm_calls: 5`，偏差 1-2 个数量级。

### 4.2 可靠性

- 全部细粒度检测器 fail-open（失败=safe），JSON 解析失败同样计入安全。
- `asyncio.gather(..., return_exceptions=True)` 在 OCR/画面评估处吞掉异常（`frame_ocr.py:194-197`），失败帧静默消失。
- 无重试、无超时预算、无熔断（除 llm_client 内部路由冷却）；Paraformer 轮询 10 分钟占住请求。
- 无磁盘/临时文件回收；无帧图片生命周期管理。

## 5. 细粒度「几帧定生死」能力验证

针对设计文档点名的两个真实痛点做代码级推演（无标注数据，无法实测，结论为能力可达性分析）：

### 5.1 场景 A：地图缺失台湾（画面 3-5 秒，地图占画面 5-20%）

**能到达的路径**：密集扫描 1fps → 若该时段帧间差异高则进 `analysis_frames` → map_auditor 对每帧调 VLM（prompt 明确点名台湾，`map_auditor.py:101-106`）→ VLM 若判 `missing_regions` 含台湾 → risk critical +30 分。

**断点**：
1. **静态地图不进细审集**：anomaly_score=帧间哈希差（`dense_frame_scanner.py:223-251`）。地图定格展示 3-5 秒时差异≈0，anomaly 低于 `anomaly_threshold_low=0.3`（`pipeline.py` 仅收集 high + 抽样 low），**整段地图可能一帧都不送审**。只有地图切入瞬间的过渡帧得分高，而过渡帧是模糊/混合画面。这是"用变化度代替风险度"的概念错误。
2. 就算送审，640x360 帧中台湾本岛约 10-20 像素宽，VLM 判断"是否绘制"可靠性中等。
3. OCR 关键词兜底反向伤害：正确地图常不逐省标注文字 → `_check_keywords` 把 台湾/南海/钓鱼岛/藏南/阿克赛钦 **全部报缺失** → 每张地图都 critical（误报爆炸）；反之错误地图若恰好有文字标注则漏报。
4. 区域放大器检测到 map 区域也不会把放大 patch 送 VLM（3.9 节），小地图（占画面 <5%）无补救。

**结论**：场景 A 当前真实检出能力 **低-中**（依赖 VLM 偶然正确 + 恰好入筛），误报率高，不满足"召回≥90%"。参考行业：问题地图自动识别专项研究（中国地理信息产业协会，2026-02）在专门检测器下精确率也才 80%，说明该任务必须"几何匹配为主、VLM 为辅"。

### 5.2 场景 B：何同学式代码文件夹暴露开源项目名（画面几帧，文件夹名占画面 <1%）

**能到达的路径**：code_tracer 的 `KNOWN_OPEN_SOURCE_PROJECTS` 含 `bytetrack`（`code_tracer.py:91`），若 VLM 从帧中读出 "ByteTrack" 字样 → 命中字典 → high 风险 +20。

**断点**：
1. 同样受 640x360 限制：0.5-1% 面积的文件夹名在缩放后约 5-15 像素宽，VLM 读不出 → `has_code=false` 或 project_name 空 → 整帧判 safe。
2. 区域放大器检测出 `code_terminal` 区域后**不送 VLM**（pipeline.py:173-178 只用区域类型做过滤），放大链路空转。
3. 字典 30 项 vs GitHub Search API 兜底：无 token 时限流 60/h（`code_tracer.py:300-331` 静默吞错返回空）；子串匹配会把 `react-components-demo` 之类误判。
4. 闪现几帧的代码画面：1fps 采样下 0.3 秒画面被采到概率 ~30%，再叠加 anomaly 入筛概率，**综合检出率远低于设计 60%**。

**结论**：场景 B 对字典内知名项目"理论可达、实测存疑"；对长尾开源项目基本不可达。**"几帧定生死"痛点目前只解决了约三分之一**，根因是：①采样粒度 1fps 抓不住闪帧；②缩帧毁小字；③放大不闭环；④知识库/几何库未真正使用。

### 5.3 两场景共性断点清单（代码级）

| 检测链环节 | 地图场景 | 代码场景 | 现状 |
|-----------|---------|---------|------|
| ① 画面被采到（1fps） | 3-5s → 3-5 帧 | 几帧 → 0-1 帧 | ⚠ 闪现场景大概率漏采 |
| ② 帧间差异分够高入细审 | 静态展示时差异≈0 | 静态展示时差异≈0 | ❌ 概念性缺陷 |
| ③ 帧分辨率保留小目标 | 640x360 | 640x360 | ❌ 小字已毁 |
| ④ 区域定位放大送审 | map 启发式弱；放大不送 VLM | code 启发式弱；放大不送 VLM | ❌ 闭环缺失 |

| ⑥ 风险升级入总分 | +30 | +20 | ✅ 融合逻辑正确 |

## 9. 技术路线建议（含金标准评测集建设）

### 9.1 第一步：止血（1-2 天）
1. 修 P0-1：`frame_sequence_analyzer.py:246` 改为 `getattr(delta_result, "extracted_frames", None) or getattr(delta_result, "frames", [])`，并补最小单测。
2. 修 P0-2：`analyzer.py` 跨模态传入真实 audio_transcript / visual_description（或无模态时跳过广播，别假装执行）。
3. 修 P0-5：所有检测器失败改为返回 `risk_level="unknown"` + `needs_review=True`，融合层把 unknown 计为保守加分而非 0。
4. 修 P0-4：`_check_keywords` 结果降级为弱信号（仅当 VLM 也判缺失时才 critical），删掉"台"单字关键字。

### 9.2 第二步：能力闭环（1-2 周）
5. **原分辨率两路帧**：密集扫描继续用 640x360 做差异评分（便宜），但入筛帧按 timestamp 回源视频抽**原始分辨率**帧（cv2 按 index 读），区域放大后送 VLM——补上 P0-3 闭环：`RegionDetail` 真正调用 `call_vlm(patch, prompt)`。
6. **静态风险画面兜底**：除差异分外增加"内容风险预筛"（轻量分类器/CLIP 零样本：地图、代码屏、旗帜、文字密集），命中即强制入细审集，解决 P1-6。
7. **闪帧通道**：对场景切换点 ±0.5s 启用**全帧率 burst 扫描**（30fps 逐帧哈希差），单帧突变即入审——解决 P1-3，成本可控（仅 burst 窗口）。
8. **地图几何检测**：模板/轮廓匹配（中国边界 + 台湾岛 + 南海诸岛位置约束）为主、VLM 确认为辅（对标 csgpc 80% 精确率路线）；把 `CHINA_REQUIRED_REGIONS` 经纬度真正用起来（区域存在性检测而非文字标签）。
9. **成本闸门**：fine_grained 预算化（如 ≤30 次 VLM/视频）：地图审核只送"预筛为地图"的帧（≤5帧）；符号检测只送预筛命中帧；并发 3-5；接入 `video_config.yaml` 到各管线构造函数。
10. Paraformer：下载 `result_url` 解析；入口先 ffmpeg 抽音频轨再上传；与 whisper 二选一（按 tier）。

### 9.3 金标准评测集建设（并行，持续）
11. **四案例标注**（tests/video/）：为 ai/fight/mhy/moon 标注时间轴风险（类别/起止时间/严重级/证据帧），建立 `tests/video/labels/*.json`；写 `tests/scripts/run_multimodal_eval.py` 跑全管线输出对比（检出率/漏报/误报/耗时/调用数/成本）。
