## 1. 执行摘要

**总评：工程叙事完整、科学内核空心、生产链路中断。** 系统在"设计文档—代码骨架—验收报告"三层形成了自洽的繁荣表象，但核心仿真引擎当前**无法被导入运行**，反事实分析是**循环算术**而非仿真，GA-S3 是**配置表演**，Memory/Reflection **不进入决策**，A/B 回测 +17.6% 等关键数字**在代码与数据中无任何产出物佐证**。

三条最重的结论：

1. **P0：`simulation/engine.py` 存在 SyntaxError**（`_load_agents` 的 `try:` 无 `except/finally`，`finally: db.close()` 游离在 `_supplement_agents` 末尾，实测 `ast.parse` 报 `line 175 expected 'except' or 'finally' block`）。由于 `simulation/__init__.py` 顶部即 `from ...engine import SimulationEngine`，**整个 simulation 包不可导入**；`enhanced_analyzer._run_phase3` 的 import 落入 `except`，`simulation_summary = {"error": ...}`。即：用户界面上的"仿真推演"步骤**每次必然失败**，传播/极化/回放在生产路径上从未运行过。
2. **P0：反事实仿真的"改善"是公式内生的，不是证据。** `_simulate_original` 把 severity 标签查表成固定分（critical=90/high=75/…），`_simulate_modified` 机械减去 `min(原分*0.4, 30)`，`_generate_modified_sentence` 是字符串杂耍（replace→`[中性表述] {sentence[:20]}...`、soften→第 5 字符插"可能"、rephrase→前缀"从另一个角度看，"）。**无论改什么、改没改对，"风险必降"是恒等式**，前端 `CounterfactualPanel` 却把它呈现为"运行仿真"后的对比结论。
3. **P0：关键验收数字无来源。** `docs/08_阶段报告/05_Phase3_AB测试验证.md` 声称 36 案例上 82.3% vs 64.7%（+17.6%），全库检索该数字**只出现在 md 报告中**，无报告 JSON、无逐案例预测、无评测脚本产出；`data/backtest/` 仅 `cases.json`（25 个用例定义），无 `report_*.json`。PHASE5 "10000 Agent ≤40 分钟""命中率≥85%"的"验证结果"是配置打印（"预估时长 20-40 分钟"）而非实测。验收报告署名"验收人：Agent"、通过率 100%。**仿真可信度在 docs/02_系统设计/14 中自己也标注为"未验证"**，与 Phase 报告的全绿互相矛盾。

**建议：立即冻结"仿真增强/反事实/GA-S3"对外口径为"实验中"，先修引擎可运行性与反事实逻辑，再用有基线的回测证明预测力，最后才谈千级/万级 Agent。**

## 2. 系统全景与数据流

### 2.1 实际存在的三套（互不相认的）"仿真"

| 栈 | 入口 | 机制 | 被谁调用 | 状态 |
|----|------|------|----------|------|
| 平台人格模拟（旧） | `persona_simulator.simulate_platforms` | 每平台 1 次 LLM（persona_{platform}.txt 模板） | `analyzer` 旧路径 | 可运行，29 平台并行 |
| 多 Agent 反应（现行主力） | `agent_simulator.simulate_all_platforms_with_agents` | 每平台现场生成 5 个人格 → 5 次 LLM 反应 → 聚合 | `enhanced_analyzer._run_phase1`、`resumable_analyzer`、`analyzer` | 可运行，每次分析约 **290 次 LLM 调用** |
| Tick 仿真引擎（V2.5） | `simulation.engine.SimulationEngine` | 时间片 + 分层 Agent + 平台仿真 + 传播模型 + 监控器 | `enhanced_analyzer._run_phase3` | **SyntaxError，恒失败** |

设计文档（08）描述的"SimulationOrchestrator 四层 Agent（A/B/C/Group）"与代码中实际的 `AgentTier`（仅 A/B/C，见 `simulation/models.py:22-26`）**不一致**；08 §3 称"替代原 Director/Watcher/Guardian 四角色"，但代码仍完整保留 director/watcher/guardian 三个 monitors 并在 `_execute_tick` 中调用。文档与实现双向漂移。

### 2.2 数据流（现状）

```
用户文案
  ├─(Phase1) assess_risks + simulate_all_platforms_with_agents  ← 真正产出用户可见"平台反应"
  ├─(Phase2) 信号关联 / 实体风险链 / StoryRiskAssociator / DynamicWeights
  ├─(Phase2.5) trait_risk_mapper 权重映射（专家表）
  ├─(Phase3) SimulationEngine.create_lightweight → ImportError → error 字段   ← 断头路
  └─(Phase4) _compile_final_report：reach>50 才 +10 分（永远走不到）；confidence 按"模块是否存在"加分
决策输出：decision_advisor 按静态分阈值（≤30 直接发布 / ≤60 修改后发布 / ≤80 暂缓 / 否则不发）
反事实：counterfactual_sim（查表+固定衰减，非仿真）→ CounterfactualPanel
```

**关键事实：最终"能不能发"的判定几乎完全由静态风险分决定；仿真对决策的唯一通路（reach>50 → +10 分）因 Phase3 失败而从不触发。**

## 3. 人格工厂真实性评估（7 层 / 人生故事 / 记忆）

### 3.1 7 层人格：三套互不兼容的 schema

| 来源 | L1 | L2 | L3 | L5 | L7 |
|------|----|----|----|----|----|
| `persona_generation.txt` / life_story | `L1_basic` | `L2_values`(政治倾向/消费主义/social_justice…) | `L3_knowledge` | `L5_correction` | `L7_evolution` |
| `engine._supplement_agents` | `L1_demographics` | `L2_personality`(openness…) | `L3_values`(political_lean) | `L5_knowledge` | `L7_narrative` |
| `rule_engine.decide` 读取 | — | `L2_values.social_justice` | — | — | — |

后果链：
- 轻量补充 Agent（`L2_personality`）喂给 `rule_engine` 时 `l2={}`，`_calc_like_prob` 的 `social_justice` 永远取默认 5.0 —— **补充 Agent 的行为与人格脱钩，等价于随机体**。
- LLM 生成的人格 `L4_behavior.active_hours` 是 `"22:00-01:00"` 形式（prompt 规定），而 `time_model.ACTIVE_HOURS_MAP` 只认"早间/午间/晚间/深夜/全天/上午/下午"——**所有 LLM 人格的时间表都走 `[(19,23)]` 默认值**，人格里的作息信息失效。
- `decision_engine` 把人格 JSON 截断到 2000 字符，7 层全文通常 1500–2500 字，**L5/L6/L7（敏感触发、社交、近期经历）随时被截掉**，而 prompt 却声称"根据你的人格特征决定行为"。

### 3.2 人格可验证性

- `QualityValidator` 有 5 条硬规则（高学历低认知、低收入高消费主义、激进潜水、高自审无触发、情绪基线矛盾）+ LLM 软校验。方向合理，但**校验对象是 LLM 生成物的一致性，不是"这个人格是否像真人/是否可预测行为"**。无 test-retest 信度、无 Big Five 复测 r>0.7 的实测（docs/01_产品与需求/04_路线图与里程碑.md 阶段 4 的 Go/No-Go 条件）。
- 原型库体量真实：`persona_archetypes.py` 3085 行 + `p1_archetypes.py` 832 行 + `p2_archetypes.py` 883 行，28 平台模板齐全——这是本模块最扎实的部分。
- **每分析一次就重新随机生成 5×29 人格**（`generate_personas_batch(..., persist=False)`），同一文案两次分析的人格样本完全不同 → 平台反应不可复现、不可对比。

### 3.3 人生故事 A/B/C 与"CGSS"

- A-tier 6 轮访谈（每轮 target_words=3000）、B-tier 人口统计采样、C-tier 模板变体——结构完整（`life_story_generator.py` 544 行，含 timeline_builder/scene_generator/narrative_integrator）。
- **`CGSS_DEMOGRAPHICS` 是 13 行手写权重表**（年龄段/性别/学历/收入/城市级别 + weight 0.05–0.12），**不是中国综合社会调查（CGSS）微观数据**。对外称"基于 CGSS 采样"属于过度声明，应改为"自建人口统计先验"。
- `story_generation/personality_evolver`：事件库 `data/events/trigger_events_db.json` 12 个事件，Big Five 按事件正负向调整并 clamp 到 [0,1]。逻辑自洽，但演化幅度是拍定的常数，无文献或数据标定。

### 3.4 Memory Stream / Reflection：实现了，但不驱动决策

- `MemoryStreamStore`（ChromaDB 三因子 Recency 0.5 / Importance 0.3 / Relevance 0.2，降级 DB 检索）与 `ReflectionEngine`（累积重要性≥10 触发，LLM 生成反思问题→反思记忆）实现完整，对齐 Generative Agents 论文形态。
- **但仿真决策链路完全不调用它们**：`decision_engine.decide_actions` 只拿截断后的 persona JSON + feed；`rule_engine` 纯概率；`agent_simulator._agent_react` 只拼 persona + prompt。Grep 全库，MemoryStreamStore 的调用方只有 `routes_v3/routes`（API）与 `story_risk_associator`。
- 细节缺陷：`reflection_engine.py:154` 对**同步方法** `memory_store.retrieve` 使用 `await`（一旦触发即 `TypeError`）；`_mark_memories_reflected` 注释自认"当前 MemoryStreamStore 不支持直接更新，这里只做日志记录"——**"已反射"标记是假的**，同一记忆会被重复反射。

**结论：7 层人格是"prompt 级真实、行为级架空"；记忆/反思是"库级真实、决策级未接线"。**

## 4. 仿真引擎科学性审视

### 4.1 预测力 vs 随机：没有被测过

- `backtest.py` 的 `direction_accuracy` 是逐案例 0/1（`predicted_direction == actual_direction`），**无随机/多数类基线、无置信区间、无显著性检验**。案例规模：`data/backtest/cases.json` 25 条 + `data/test/paperwork` 36 条。
- docs/02_系统设计/04_仿真运行层.md 要求"A-tier 与 C-tier 反应差异度 > 0.4""极化灵敏度 > 0.7"，代码中**无对应测量实现**。
- docs/02_系统设计/07_仿真验证与迁移.md 的 Go/No-Go（方向准确率>55% 且 V2 提升>10%）在 `backtest.py` 有判定代码，但 `data/backtest/` 下**无任何 report_*.json 实测结果**；`tests/scripts/quick_backtest.py` 是读报告的打印脚本（且写死 `/workspace/data/backtest` 路径），跑不出数字。
- **当前没有任何证据表明仿真输出优于随机猜测。**

### 4.2 GA-S3 分群：是表演，不是机制

- `group_agent.py`（495 行）实现完整：DistributionSpec 高斯采样、StanceDistribution、`from_persona_list` 统计聚合、蒙特卡洛个体生成、`generate_reactions` 聚合。
- **但全库无一处 `GroupAgent(` 实例化**（仅 `simulation/__init__.py` 导出）。`AgentTier` 枚举无 Group 层级。`scale_manager.build_engine_config` 产出 `group_count/enable_group_agent/group_size_per` 等键，`SimulationEngine.__init__/_supplement_agents` **从不读取**，仍按 `i < count//2` 粗暴分 A/B/C（轻量模式约一半 Agent 被标为 A 级，与设计 5% 严重不符）。
- "等效 10 万个体"来自 `TierAllocation.equivalent_individuals` 的**乘法**（group_count × group_size_per），不是运行时统计。**GA-S3 = 配置算术，不是仿真能力。**
- 即便接线，其立场采样 `political_lean`（左/中/右 → ±0.5）与内容立场无标定关系，Group 反应仍是"活跃度概率 × 立场对齐阈值（0.7/0.4/-0.5）"的硬编码阶梯。

### 4.3 传播动力学参数：全部无出处

| 参数 | 取值 | 出处 |
|------|------|------|
| 阶段阈值 reach | 10 / 100 / 500 | 无 |
| 主流化动能阈值 | 3.0 | 无 |
| 极化阈值 | 0.4 | 无 |
| 消退判定 | 动能连续 3 tick 下降 | 无 |
| 情感强度 | 0.7×负 + 0.3×正 | 无（假设负面驱动动能，未验证） |
| 点赞/转发基础概率 | 0.02–0.3（按影响力档） | 无 |
| C 级互动概率 | 潜水 0.05 … 创作者 0.5 | 无 |
| Group 立场对齐行为阈值 | 0.7 / 0.4 / -0.5 | 无 |

- 立场提取 `extract_stance_values`：任何 like/share 一律 +0.5、dislike 一律 -0.7、文本用关键词子串计数（`"好"` 命中 `"不好"`，`"过分"` 重复入负向词表）——**极化指数输入本身不可信**。缓解项：极化算法用 Sarle 双峰性系数（BC，有统计学定义）是本模块最接近"有出处"的部分。
- "5 阶段传播"名实不符：`SpreadStage` 枚举是 **6 阶段**（seed/primary/community/polarization/mainstream/fading），08 文档摘要写"种子→扩散→爆发→长尾→沉淀"（又是另一套 5 阶段命名）。三处口径互不相同。
- `spread_model.update` 的 `stage_history` 记录 `from_stage` 时写成了 `self.current_stage.value if not stage_changed else ""`——变更时反而写空串，**阶段迁移轨迹是坏的**。

### 4.4 分层决策引擎

- B 级：`decide_actions` 单次 LLM，persona 截断 2000 字，无记忆检索，失败降级为"看一条帖子"。
- C 级：规则概率 + 4 类模板评论（激进/直率/中立/温和/谨慎各 4–5 句），**评论模板与人格维度无映射**，只看 `expression_style` 字符串。
- **A 级从未参与 tick**：`_execute_tick` 只调 `_b_agent_tick` 与 `_c_agent_tick`，`agent_tiers` 里的 A 级 Agent 是僵尸（不感知、不决策、不产出）。设计中"KOL 每步独立 LLM、引爆传播"完全不存在。

## 5. 反事实分析有效性

**判定：无效——它是"改写评分公式"，不是"反事实仿真"。**

1. **基线不是仿出来的**：`_simulate_original` = severity 查表均值（critical→90 … green→10）。同一文案改一个字不改 risk_items，"仿真"分不变。
2. **处理组是算出来的**：`_simulate_modified` 规则路径 `reduction = min(原分*0.4, 30)`，**固定衰减 40%**。overall_improvement 因此恒 ≥0（除非 LLM 路径覆盖）。`_generate_recommendation` 的话术（"预计风险可降低 X 分"）建立在这个恒等式上。
3. **修改策略是占位符**：delete 尚可；replace 输出字面量 `[中性表述] {原句前20字}...`；soften 在第 5 字符插入"可能/或许"；rephrase 加前缀"从另一个角度看，"。这些改写**不保证语义、不保证风险点被消解**，却直接进入"修改后"评分。
4. **LLM 路径时序倒置**：`_llm_simulate` 是让 LLM 对比原文/改写文预测分数——即便成功，也只是"LLM 看两段文字打分"，不经过任何 Agent/传播过程，且失败静默回落到上面的固定衰减。
5. **平台反应是线性化妆**：`_estimate_platform_reactions(risk_score)` = `neg=risk/100`，douyin/xiaohongshu 加固定偏移（+0.05/+0.1）。与平台真实用户结构无关。
6. 用户价值：`CounterfactualPanel.vue` 展示"修改前 → 修改后 + N 分"的对比 UI，**制造了强因果暗示**。用户据此改文案，得到的是安慰剂。

**有效性修复方向（见 §10）：改写必须由 LLM/规则针对具体风险句生成且保留语义；改写后必须重跑同一套静态评估（而不是衰减原分）；只有当评估器可复现时，前后差值才可解释。**

## 6. 性能与可复现性

### 6.1 成本与时延（实测可推算部分）

| 路径 | LLM 调用 | 备注 |
|------|----------|------|
| Phase1 平台反应（现行） | 29 平台 × (5 人格生成 + 5 反应) ≈ **290 次/分析** | 人格每次重新生成，无缓存 |
| 旧 persona_simulator | 29 次/分析 | 仍在 analyzer 兜底路径 |
| Phase3 轻量仿真（100 Agent × 36 tick） | 设计 ≤200 次 | **从未跑起来** |
| 反事实 4 策略 | 0–4 次（可选 LLM） | 规则路径 0 次 |

docs/02_系统设计/04_仿真运行层.md 预算（quick ¥0.5 / standard ¥2 / deep ¥5 / large ¥10–20）未在代码中做**运行时成本核算**（`total_cost` 字段在编排器草稿里，engine 无计量）。290 次/分析的成本远超"quick ¥0.5"的想象，且全部花在与决策弱相关的平台反应文本上。

### 6.2 可复现性：接近于零

- 全库 `random.random()/random.sample/random.choice/gauss` **无 seed 注入**；LLM 调用无 temperature/seed 固定策略记录。
- 人格、变体种子、补充 Agent、规则概率、Group 采样全部随机；同一文案两次分析的 `platform_reactions` 必然不同。
- 结果无 run-config 快照（模型名、prompt 版本、seed、Agent 清单哈希）；`consistency_checker` 依赖"跑 3 次"在**不可复现的系统上**测一致性，其"一致性低→低置信度"的下游处理是对随机性的安抚，不是对模型的验证。
- `prompt_version_manager` / `prompt_ab_test_runner` 已存在但未与仿真结果绑定版本号。

### 6.3 规模声称 vs 现实

- 代码真实规模：Phase1 = 每平台 5 Agent（29 平台）；轻量引擎 = 100 Agent 36 tick（若能运行）。
- 文档声称：100 / 500 / 2000 / 10000 Agent + GA-S3 等效 10 万。**除 scale_manager 的配置表外无运行证据**；PHASE5 验收文本本身写的是"预估时长"。

## 7. 用户价值 vs 工程炫技

### 7.1 用户能看懂的部分（正向）

- 前端有完整叙事链：`AnalysisPipeline`（风险评估→信号采集→**仿真推演**→报告生成）、`PlatformReactions`（28 平台差异化反应）、`PolarizationChart`、`PropagationGraph`、`CounterfactualPanel`、`RiskGauge`。**产品形态是清楚的**：发前先看各平台会怎么吵。
- `decision_advisor` 的四档结论（直接发布 / 修改后发布 / 暂缓发布 / 不建议发布）+ 修改优先级，是用户真正要的决策物。

### 7.2 用户感知不到却花了大钱的部分（负向）

| 工程投入 | 用户可感知增量 |
|----------|----------------|
| memory_stream + reflection_engine（ChromaDB、三因子、反思链） | 0（未接入决策） |
| GA-S3 group_agent 495 行 | 0（未实例化） |
| scale_manager 4 档规模 | 0（配置 API 可见，行为无变化） |
| monitors director/watcher/guardian | 0（引擎不可运行） |
| replay/timeline 回放、propagation_tree 传播树 | 0（同上） |
| personality_evolver 人格演化 | 0（演化结果不进 Phase1 反应 prompt） |
| counterfactual_sim 358 行 | **负**（错误信心） |
| platform_immersion / hybrid_retriever / video_embedding_store | 间接（服务博主视频知识，与仿真无关但属合理旁路） |

### 7.3 结论性的产品判断

**"能不能发"的问题其实静态 7 维评估 + 修改建议就能回答 80%，当前仿真体系既没有证明那额外 20%，又在 UI 上占了"仿真推演"的一步（还恒失败）。** 过度工程的根源是把"仿真可信"当成了已达成（验收报告全绿），而非待证伪的假设。

## 8. 学术对标

| 维度 | Generative Agents (Park et al. 2023) | Concordia (DeepMind, arXiv:2312.03664) | OASIS (arXiv:2411.11581) | SoMe (AAAI, arXiv:2512.14720) | AgentSociety / 舆论动力学 | VibeUtopia 现状 |
|------|------|------|------|------|------|------|
| 规模 | 25 Agent 小镇 | 可配置社群 | **100 万 Agent** 社交平台 | 任务基准 | 千–十万级 | 声称 100–10000，实测 5×29 |
| 记忆 | 记忆流+反思**驱动行为** | 记忆组件可插拔并进决策 | 简化记忆 | — | 各异 | 有实现，**不进决策** |
| 验证 | 模仿/访谈/对照实验 | 技术报告+示例回归 | 与真实平台数据对照（涨粉/转发趋势） | **公开数据集+排行榜** | 与真实事件校准 | 无可信实测 |
| 可复现 | 公开代码 | 公开+CI | 公开+数据集 | 公开 benchmark | 部分 | 无 seed/无 run-config |
| 传播模型 | 无（行为仿真） | 无（组织仿真） | 平台推荐+互动机制 | 评测集 | Deffuant/HK/Ising 等**有标定阈值** | 6 阶段启发式，阈值无出处 |
| 极化 | — | — | 有情感/立场演化分析 | — | 双峰/阵营检测有文献 | BC 双峰系数（可用）但立场输入是关键词启发 |

要点：
1. **记忆/反思"是否真影响决策"是本领域区分玩具与系统的第一性问题**——Park 等人用消融实验证明反思对行为一致性有贡献；VibeUtopia 把反思做成了孤立子系统，恰好丢掉了这一验证。
2. **OASIS 的说服力来自"仿真结果 vs 真实平台数据"的对照**；VibeUtopia 的对照只有"改写前 vs 改写后（公式）"。
3. **SoMe 提供了现成的社交 Agent 评测集**——VibeUtopia 完全可以借它的任务测"仿真 Agent 是否优于基线 LLM 直答"，这是补预测力验证的捷径。
4. 舆论动力学（02_Opinion_Dynamics/public_opinion_llms 等）中阈值/置信参数通常来自文献或拟合；VibeUtopia 的传播参数是产品拍脑袋，**应至少标注"启发式默认值，未标定"**，或做一次历史事件拟合。
5. 本地参考库质量高（oasis/concordia/SoMe/MemGPT/MiroFish 源码在 `references/projects/`），**对标材料充足但未转化为实现约束**。

## 10. 简化/强化路线（何时用全仿真，何时用快速启发式）

### 10.1 决策树：什么问题需要什么算力

```
用户问题                     推荐路径                         是否需要 Agent 仿真
───────────────────────────────────────────────────────────────────────────
这句话有没有风险？             静态 7 维评估 + 证据链            否
哪个平台更危险？               平台画像权重 + 平台化改写建议      否（1 次 LLM/平台即可）
怎么改更安全？                 针对风险句的 LLM 改写 + 重评估    否（禁止用"固定衰减"）
会不会吵起来/吵成什么样？       中等规模仿真（100–500 Agent）+ 传播/极化   是（仅此档）
改这句 vs 改那句，哪个更能降舆论风险？  反事实 = 改写→重评估→对比（可加小规模仿真）  可选
趋势/长尾预测                  历史事件回测标定后的传播模型        是（需先有预测力证明）
```

### 10.2 三步走（可执行顺序）

**Step A（1–2 周）：止血与诚实化**
1. 修 `engine.py` try/finally 结构（P0-1），补最小 smoke 测试（import + 3 tick）。
2. 重写 `_generate_modified_sentence`（LLM 按风险句生成语义保留改写）与 `_simulate_modified`（**重跑静态评估**，删除 40% 衰减）；UI 文案从"仿真"改为"改写效果预估"，直至有真仿真（P0-2）。
3. 验收报告与对外口径标注数字来源；无产出物的指标一律改"未验证"（P0-3/P0-4）。
4. 统一 7 层 schema 为 `persona_generation.txt` 一套，engine/rule_engine/time_model 全部对齐；`active_hours` 统一为枚举（P1-3）。

**Step B（2–4 周）：证明"有预测力"再谈规模**
1. 用 `data/test/paperwork` 36 案 + `cases.json` 25 案建立可复跑回测：固定 seed、固定 prompt 版本、输出逐案例预测 JSON。
2. 引入基线：多数类 / 静态关键词 / 直接 LLM 打分（无 Agent）三对照；指标含准确率、方向准确率、bootstrap 95% CI；未超基线则停仿真扩展（对齐 docs/02_系统设计/07_仿真验证与迁移.md Go/No-Go）。
3. 可选用 SoMe benchmark 任务测 Agent 反应质量。
4. 传播/极化参数标注"启发式"，并做一次 3–5 个已知舆情事件的阈值拟合或敏感性分析。

**Step C（按需）：把仿真用在刀刃上**
1. 仅当问题类型为"会不会吵起来"才启用仿真；入口用轻量（100 Agent）起步，A 级真正接管 KOL 行为（修 P1-4）后再加 B 级采样 LLM。
2. Memory/Reflection：要么接入 `decide_actions`/`_agent_react`（并在回测里做"有记忆 vs 无记忆"消融），要么移出主线避免空转。
3. GA-S3：只有在需要覆盖长尾量时才接线（engine 消费 group_count），并把"等效个体"改为运行时统计口径；接线前删掉对外的 10 万等效话术。
4. 反事实最终形态：改写 → 重评估（必做）→ 小规模仿真对比（可选）→ 输出"改写建议 + 预估区间 + 置信度"。

### 10.3 简化红线

- 任何"仿真结论"必须能回答：**对照基线是什么？样本多少？区间多宽？seed/版本是什么？** 答不出就只配叫"启发式参考"。
- 单次分析 LLM 预算硬闸门（例如默认 ≤80 次，超出走 C 级规则），杜绝 290 次无计量调用。
- 一套仿真栈：废弃 `persona_simulator` 旧路径与死配置（scale_manager 中 engine 不读的键），保留 `agent_simulator`（快速启发式）+ `simulation.engine`（真仿真）双档即可。
