# QA测试体系审计

> **文档定位**：调研审计｜测试覆盖、门禁、回归与缺陷管理审计
> **所属目录**：`docs/05_调研审计/`


- 审计对象：VibeUtopia 全仓库（backend / frontend / tests / scripts / data / docs）
- 审计日期：2026-05-18
- 审计方式：测试资产盘点、pytest 实际收集与抽样执行、配置与 CI 检查、报告与记忆交叉核对
- 实测环境：Python 3.12（Anaconda），`PYTHONPATH=src`，pytest + pytest-asyncio

---

## 1. 执行摘要

项目已沉淀一批**有价值的测试资产**：50 个左右的 pytest 风格用例、4 组真实视频案例（tests/video，Git LFS）、36+ 篇文案黄金案例集（data/test/cases）、25 条结构化回测案例（data/backtest/cases.json）、Prompt A/B 测试运行器、多轮一致性检查器（consistency_checker）、以及 PHASE2-6 验收报告。**评测素材的丰富度明显高于行业同类 LLM 应用项目的平均水平**。

但**自动化测试体系基本处于"有素材、无门禁"状态**，核心事实如下：

1. **测试套件当前无法一键运行**：仓库无 `pytest.ini` / `pyproject.toml` / `conftest.py`，默认收集 8 个文件全部 ImportError；必须手工设置 `PYTHONPATH=src` 才能收集到 37 个用例。
2. **套件当前是红的**：实测 1 个断言失败（test_platform_weights，期望 P1 平台 4 个实际 14 个，V3.1 平台扩展后未同步），2 个文件收集期崩溃（test_llm_models 强依赖 API Key；test_platform_immersion 触发 `ImportError: cannot import name 'ImmersionRecord' from 'backend.models'` —— **被测代码本身已损坏**）。
3. **零 CI、零质量门禁**：无 `.github/`，`.trae/rules/compile-test.md` 规定的"改代码必须跑 pytest"没有任何自动化强制手段，全靠自觉。
4. **API 契约测试为零**：routes*.py 共约 90 个端点（routes_v3.py 48 个），tests 中仅有"路由模块可导入"级别的冒烟；tests/logs/T1_VALIDATION_TEST_OUTPUT.log 显示真实运行时已出现 4 个 HTTP 404。
5. **前端零测试**：Vue3 + Naive UI 前端无 vitest/cypress/playwright，package.json 无 test script，21 个组件 + Workbench 视图仅靠 vue-tsc 类型检查。
6. **tests/video 四案例（约 400MB，12 文件）未被任何自动化代码引用**：test_with_real_cases 仅校验硬编码字符串长度，多模态管线（frame_risk / keyframe / OCR / audio_transcriber）无自动化验证。
7. **LLM 非确定性已有工程雏形**（一致性检查、回测命中率、Prompt A/B、可信度分级），但未接入任何回归门禁，属于"手工评测脚本"而非"评测框架"。

**总体判断**：测试资产 6/10，测试执行自动化 2/10，质量门禁 1/10。优先级最高的是"让测试能一键跑起来并修红"，其次是 API 契约与 LLM 评测回归化。

## 4. LLM/非确定性系统专项测试方法

### 4.1 现状评估

项目对非确定性有**正确的问题认知**（PHASE5 一致性>60%、可信度分级、A/B 对比、命中率），但实现形态是"一次性评测脚本 + 报告"，不是"可持续回归的评测体系"。对照业界 LLM 应用测试（prompt regression / golden set / eval harness）：

| 业界实践 | 项目现状 | 差距 |
|---------|---------|------|
| Golden set 常驻回归 | data/test/cases（36+25 条）存在但无自动 runner 绑断言 | 案例集未代码化为测试 |
| Prompt 回归（改 prompt 必跑评测） | prompt_version_manager + A/B runner 存在 | 未设门禁：改 prompts/*.txt 不会触发任何验证 |
| 确定性基线（temperature=0 / seed / 录制回放） | 无 | 单测与 LLM 真调用未分层 |
| 结构化输出校验（JSON schema / pydantic） | 部分解析逻辑散落各 service | 无统一输出契约测试 |
| LLM-as-judge / 评分器 | 无（A/B runner 用规则比对 expected_level） | 可引入但需先固化规则基线 |
| 多样本稳定性（n 次采样通过率） | consistency_checker（3 次仿真） | 未覆盖单 prompt 输出维度 |
| 成本/延迟预算 | large_scale_model_test 手工记录 | 无预算断言（回归时成本暴涨无法拦截） |
| Mock/Stub 分层 | 仅 test_platform_immersion 使用 unittest.mock | 其余测试直连 ChromaDB/LLM/DB |

### 4.2 建议的专项测试策略（详见第 7 节）

1. **分层**：L0 纯逻辑（mock LLM，确定性断言）→ L1 契约（输出 schema、字段完整、分数区间）→ L2 评测（golden set 命中率/一致性，nightly，允许波动阈值）→ L3 人工抽检（报告可读性、改写质量）。
2. **Prompt 回归门禁**：任何 `src/backend/prompts/**` 变更 → 自动跑 golden set 子集（25 条 backtest/cases.json）→ 命中率跌幅 >5% 即阻断。
3. **非确定性断言范式**：不用全文相等，改为（a）风险等级枚举相等或在允许邻域内；（b）维度分数落在期望区间（backtest_cases.py 的 score_range 已支持）；（c）关键证据关键词命中（key_evidence 已定义）；（d）3 次采样多数投票一致。
4. **录制回放**：对 LLM 调用层（llm_client.call_llm）加 cassette 机制，单元/CI 用回放，评测任务才打真实模型。
5. **一致性指标入门槛**：把 consistency_checker 的综合一致性>60% 作为发布前必跑项，并输出可信度标注供决策层消费。

## 5. 回归与 CI 现状

### 5.1 CI

- **不存在**。无 `.github/`、无其他 CI 配置（references/ 下的第三方 CI 不计）。
- 后果：合并前无任何自动验证；测试红了也没有人被阻断（lastfailed 22 项长期存在可佐证）。

### 5.2 质量门禁

| 门禁 | 规范出处 | 自动化 |
|------|---------|--------|
| Python 改动必须 pytest 通过 | compile-test.md | 无 |
| 前端改动必须 vue-tsc 通过 | compile-test.md | 无（build script 含 vue-tsc，但无 CI 调用） |
| 修 Bug 先写失败用例 | compile-test.md + CLAUDE.md | 无（无覆盖率/增量测试检查） |
| 核心模块变更必须回归 | compile-test.md | 无 |
| 0 错误 0 警告才能提交 | 全局规范 | 无（requirements 无 lint 工具声明；仓库有 .ruff_cache 说明本地用过 ruff，但无配置文件） |
| 覆盖率 | compile-test.md 提到 --cov | pytest-cov 未在 requirements.txt |

### 5.3 回归策略现状

- 回归资产是"脚本 + 报告"：backtest_full.py（直接调风险评估模块，跳过仿真耗时步骤）、run_prompt_ab_test.py、large_scale_model_test.py。
- 回归触发靠人：MEMORY.md 明确"Windows 环境 bash 工具无法捕获命令输出，测试需手动运行"——工作流摩擦进一步降低回归频率。
- 历史验收（PHASE2 命中率 85%、PHASE5 一致性机制）证明**回归能力曾经被行使过**，但没有固化为每次变更必过的流水线。

## 7. 测试策略建议（金字塔、评测集、自动化路线）

### 7.1 目标测试金字塔

```
              ┌─────────────┐
              │  E2E (少量)  │  Playwright：上传→分析→报告 主流程 ×3 案例
              ├─────────────┤
              │  API 契约    │  TestClient：90 端点冒烟 + schema 校验 + 错误码
              ├─────────────┤
              │  集成测试    │  DB/Chroma/Neo4j fixture；多模态管线对 tests/video 4 案例
              ├─────────────┤
              │  LLM 评测层  │  golden set 命中率/一致性/区间断言（nightly，非 PR 门禁）
              ├─────────────┤
              │  单元测试    │  纯逻辑大批量：权重/聚合/规则引擎/时间模型/解析器（mock LLM）
              └─────────────┘
```

比例目标（6 个月）：单元 70% / 集成 15% / 契约 10% / E2E 5%，LLM 评测独立轨道不计入金字塔。

### 7.2 评测集与 LLM 回归设计

1. **固化三套黄金集**（均已存在，只需绑定 runner）：
   - 文案风险集：`data/test/cases/paperwork/` 36 条 + `data/backtest/cases.json` 25 条 → 断言风险等级、高危维度、分数区间（backtest_cases.py 的 RiskDimensionExpectation / score_range / key_evidence 字段直接可用）。
   - 多模态集：tests/video 4 案例 + data/video_transcripts 真值 → 断言转写质量、跨模态冲突检出、帧风险标注。
   - Prompt A/B 集：恢复 data/ab_test_cases.json 15 条 → 每次 prompt 版本发布跑双版本对比。
2. **断言范式**：枚举相等 / 区间包含 / 关键词命中 / 3 次采样多数一致；禁止全文字符串比对。
3. **门禁分层**：PR 必过 = 单元 + 契约 + mock 集成（<5 分钟）；nightly = 真实 LLM 评测 + 一致性检查 + 性能基准；发布 = 命中率≥基线-5% 且一致性>60% 且可信度≥中可信。
4. **Prompt 变更协议**：prompts/** 任何 diff → 自动跑 25 条回测子集 → 报告命中率前后对比 → 跌幅超阈值阻断合并（与 prompt_version_manager 的版本号/回滚机制打通）。

### 7.3 自动化路线图

| 阶段 | 周期 | 内容 | 出口标准 |
|------|------|------|---------|
| A. 修红与可运行 | 1 周 | pytest.ini + conftest（pythonpath、markers: unit/integration/llm/e2e/slow）；修复 ImmersionRecord；更新 28 平台断言；API Key 测试改 skipif；补 scripts/run_tests.ps1 | `pytest -m unit` 本地一键绿 |
| B. 门禁上线 | 1 周 | CI（pytest unit+contract、vue-tsc、ruff）；TestClient 全端点冒烟 + OpenAPI 快照；pytest-cov 基线 | PR 红灯阻断生效 |
| C. 覆盖补齐 | 2-3 周 | analyzer/risk/simulation-rule/signal 纯逻辑单测；Chroma/DB fixture 化；LLM 录制回放层 | 核心模块覆盖≥60% |
| D. 前端与 E2E | 2 周 | Vitest（store/api/关键组件）+ Playwright 3 条主流程 | 前端 smoke 绿 |
| E. LLM 评测回归化 | 2-3 周 | eval harness 绑黄金集；prompt 回归门禁；一致性 nightly；成本/延迟预算 | 改 prompt 有自动回归证据 |
| F. 性能与安全 | 2 周 | 仿真基准（100/1000/10000 Agent）；k6 API 压测；路径遍历/Prompt 注入/密钥扫描 | 有基线数据与告警阈值 |

### 7.4 测试数据管理建议

- **tests/video**：保持 Git LFS 与"不可删除"红线；新增 `tests/video/MANIFEST.md` 记录每个案例的风险标签与期望输出，使其成为多模态黄金集的正式成员（当前仅是"素材堆放"）。
- **黄金集版本化**：data/test/cases 与 cases.json 变更走 review；补充案例编号规范（与 backtest_cases.py 的 case_id 对齐）。
