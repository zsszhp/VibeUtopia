## 2. 逐项实施细节

### 2.1 P0-1 severity 词表错配（红线保底/交叉叠加失效）

**根因**（审计 06 §3.1、§5.2-1）：

- Prompt `risk_assessment_v2.txt` 强制输出四档 `green/yellow/orange/red`。
- `analyzer.calculate_overall_score` 用 `severity == "high"` 收集 `high_dims`（原 `analyzer.py:135`），导致规则 1「任一维度 HIGH 则整体≥50」与规则 2「多维 HIGH +15」**永不触发**。
- 同类错配还分布在：风险预警广播（`severity in ("high","critical")`）、改写触发（`severity in ("high","medium")`）、`enhanced_analyzer` 改写触发——LLM 服从 Prompt 时全部失效。

**修复**：

1. 新增 `src/backend/services/severity.py` 作为**唯一映射层**：

   | 输入词表 | 判定档位 | 对外四档 |
   |---------|---------|---------|
   | green / low / safe / none | low | green |
   | yellow / medium / moderate | medium | yellow |
   | orange / elevated | elevated | orange |
   | red / high / critical / severe | high | red |

   - `severity_level(sev, score)`：任意词表 → 判定档位；未知词表按分数兜底（对齐 Prompt 标定 0-25/26-50/51-75/76-100）；`medium` 档 `score>=60` 细分为 elevated（与历史 `_normalize_severity` 行为一致）。
   - `is_high_severity(sev, score)`：`red/high/critical` 为高档；**`score>=76` 时即使 severity 缺失/错标也判高档**（防止 LLM 词表服从失败再次导致保底失效）。
   - `normalize_severity` / `score_from_severity` / `needs_rewrite` / `is_elevated_or_above` 供落库、改写、预警统一使用。

2. `analyzer.calculate_overall_score`：`high_dims` 判定改为 `is_high_severity(severity, score)`。
3. `analyzer.run_analysis`：风险预警广播改用 `is_high_severity`；改写触发改用 `needs_rewrite`；落库用的 `_normalize_severity`/`_score_from_severity` 收敛到映射层（删除内嵌副本）。
4. `enhanced_analyzer` 改写触发同步改为 `needs_rewrite`。

**验证**（`tests/test_p0_algorithm_fixes.py::test_severity_mapping_red_triggers_floor`）：

- 单个 red 维度（score=10）→ overall=50（保底触发）✅
- 双 red 维度（score=30×2）→ overall=65（保底 50 + 交叉叠加 15），cross_effects 生成 1 条 ✅
- 旧词表 `high` 兼容 → overall=50 ✅
- 全绿（score=5）→ overall=5（保底不误触发）✅
- 审计 §5.3 BT007 演示场景（red 80 + orange 70 + orange 65 + 8×green）→ overall=64（修复前为 64→64 不变，但 high_dims 已识别 red 维度；总分抬升主要来自红线 1.5 倍放大与 max×0.8，保底规则现已可达）✅

> 说明：BT007 期望 red/76+ 的完整达标还依赖审计 P0-3「红线规则无代码强制」（强制抬升至 76+），该条**不在本次 P0 清单内**，已在 §4 列出。

### 2.2 P0-2 evidence_chain 交叉验证结构性失效

**根因**（审计 06 §3.4-1）：

- `_cross_validate` 在 `dim.get("risk_sentences", [])` 中找相同句子。
- Prompt Schema 中 `risk_sentences` 是**顶层字段**，dimension 对象内没有 `risk_sentences` → 该字段恒为空列表，`cross_validation` 恒空，`get_summary().cross_validated_count` 恒 0，置信度交叉验证加分永不生效。
- 附带字段错配：`primary_evidence.text` 取 `risk_sentence.get("text")`，而 Schema 字段名是 `sentence`；`build_chains_for_task` 取 `rs.get("score")`，而 `risk_sentences` 无 score 字段（分数在维度对象上）。

**修复**（`src/backend/services/evidence_chain.py`）：

1. `_cross_validate` 取数源改为**任务级顶层 `risk_sentences`**（`build_chains_for_task` 传入 `all_risk_sentences`），按归一化句文本（去空白/标点）跨维度匹配，跳过同维度与自身。
2. 佐证记录补充维度分数/严重度（从 `all_dimensions` 查表，兼容风险句自带字段）。
3. 新增 `_sentence_text()`：优先 `sentence`，兼容旧字段 `text`。
4. `build_chains_for_task`：score 优先取风险句自带，否则回退对应维度的 score。
5. `assessment_basis.reasoning` 兼容 `evidence` 字段（Prompt 里说明写在 `evidence`）。

**验证**（`test_evidence_chain_cross_validation`）：

- 两条不同维度风险句引用同一原文 → 各自 `cross_validation` 填充 1 条 ✅
- `cross_validated_count == 2` ✅
- 有交叉验证的链置信度 0.95 > 无交叉验证 0.7 ✅
- 无共现句的链 `cross_validation == []` ✅

### 2.3 P0-3 帧序列空转（V3.5 全链路失效）

**根因**（审计 07 §1-1）：`frame_sequence_analyzer.analyze` 读 `getattr(delta_result, "frames", [])`，而 `DeltaFrameResult` 的帧列表属性是 `extracted_frames`（`delta_frame_extractor.py:83`）→ 序列描述/因果链/动作事件/视频-文案冲突永远拿到空列表，静默返回「无可用帧数据」。

**修复**（`src/backend/services/frame_sequence_analyzer.py`）：

```python
frames = getattr(delta_result, "extracted_frames", None)
if frames is None:
    frames = getattr(delta_result, "frames", [])
frames = frames or []
```

优先 `extracted_frames`，兼容仍用 `frames` 命名的调用方；docstring 同步更正。

**验证**（`test_frame_sequence_attribute`）：带 `extracted_frames` 的假 DeltaFrameResult 读出 2 帧；旧式 `frames` 属性仍兼容 3 帧；空帧列表走「无可用帧数据」而非属性缺失 ✅

### 2.4 P0-4 analyzer 跨模态仪式步骤

**根因**（审计 07 §1-2、§3.7）：`analyzer.py` 调用 `detect_conflicts(text=text, visual_description=None, audio_transcript=None)`，模态计数恒=1，恒返回「单模态内容，无需跨模态检测」——主分析器里的跨模态冲突检测是仪式性的。

**修复**（向后兼容，仅新增可选参数）：

1. `analyzer.run_analysis(task_id, text, depth, visual_description=None, audio_transcript=None)`：有画面描述/转写时传入真实值。
2. `video_extractor.extract_video_text` 返回值增加 `ocr_text` / `audio_text` 分模态字段（原 `text`/`source` 等字段不变）。
3. `routes.py`：收集 `visual_parts`（OCR 画面文字、`type=="visual"` 文本项）与 `audio_parts`（音频转写、Paraformer 转写、`type=="audio"` 文本项），传入 `run_analysis`。

**验证**（`test_cross_modal_receives_real_values`）：

- 仅文本 → 仍正确短路「单模态内容，无需跨模态检测」✅
- 文本+画面+音频 → 摘要不再是单模态短路，进入检测链路（本机 LLM 限流时走规则兜底，`has_hidden_risk=True` 正确识别文案安全但画面/音频含敏感词）✅

### 2.5 P0-5 失败策略 fail-open → unknown/needs_review

**根因**（审计 07 §1-5）：VLM/JSON 解析失败时各检测器一律返回 `risk_level="safe"`——与风控产品「失败应升警」的直觉相反，造成系统性漏报。

**修复（选 2 处最关键的）**：

| 位置 | 修复 |
|------|------|
| `frame_risk.py` `_parse_response` | 解析失败返回 `risk_level="unknown", needs_review=True`（原 `safe`） |
| `frame_risk.py` `_rule_based_assess` | VLM 不可用降级改为 `unknown` + `needs_review=True`（原 `safe`） |
| `frame_risk.py` `assess_video_frames` 聚合 | 任一帧失败/未知 → `VideoRiskResult.needs_review=True`；全部未知时 `overall_risk_level="unknown"` 而非 safe |
| `map_auditor.py` `audit_frame` | VLM 失败 / 帧不存在返回 `risk_level="unknown", needs_review=True, confidence=0.0` |
| `map_auditor.py` `audit_video_frames` 聚合 | `needs_review` 上抛；unknown **不计入** `has_map_risk`（不冒进加分），但**不得被当作安全** |
| `pipeline.py` | `FineGrainedRiskReport.needs_review` 字段；地图审核失败/未知时置位并记入 key_findings；`risk_order` 加入 `unknown` 档（不参与风险升级） |

**未改、仅记录的 fail-open 位置**（见 §4）：`symbol_detector.py:105-111`、`code_tracer.py:163-169`、`temporal_anomaly` 解析失败路径。

**验证**（`test_fail_open_to_unknown`）：

- `_parse_response("这不是JSON")` → `risk_level=unknown, needs_review=True` ✅
- 规则降级 → `unknown` + `needs_review=True` ✅
- 两个失败帧聚合 → `needs_review=True, has_map_risk=False`（未知≠地图风险，但也≠安全）✅

## 6. 结论

审计两份报告中标记的 5 项 P0（算法正确性）已全部修复并通过断言验证：

1. Prompt 四档与代码判定已统一到同一映射层，red 维度可触发保底分数逻辑，多维 red 可触发交叉叠加。
2. 证据链交叉验证从顶层 `risk_sentences` 取数，合规输出下可正常填充并影响置信度。
3. 帧序列分析链路读取正确属性，序列描述/因果链/动作事件恢复可达。
4. 主分析器跨模态冲突检测在有多模态输入时不再仪式性跳过。
5. 最关键的两处检测器（frame_risk / map_auditor）失败策略由 fail-safe 改为 unknown + needs_review，聚合层不再把未知当安全。

既有 API 未破坏，全量测试 55 passed 无回归。剩余 fail-open 点（symbol_detector / code_tracer）与红线强制抬升已列入 §4 待办，不得对外宣称已解决。
