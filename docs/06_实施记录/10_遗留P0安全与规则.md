### 3. fail-open 补齐：symbol_detector / code_tracer

对齐 `frame_risk.py` / `map_auditor.py` 已建立的失败策略：**解析/VLM 失败不得判 safe，置 `unknown` + `needs_review=True`，置信度 0**。

| 文件 | 原行为（fail-open） | 新行为 |
|------|---------------------|--------|
| `symbol_detector.py` `detect_frame` 帧缺失 | `risk_level="safe"` | `risk_level="unknown", needs_review=True` |
| `symbol_detector.py` `detect_frame` VLM 失败 | `risk_level="safe", "VLM检测失败"` | `risk_level="unknown", needs_review=True, confidence=0.0` |
| `symbol_detector.py` `_vlm_detect_symbols` JSON 解析失败 | 返回 `{"has_sensitive_symbol": False}`（当"无风险"） | 返回 `None`（交由上层置 unknown） |
| `symbol_detector.py` `detect_video_frames` 聚合 | 无 `needs_review`；unknown 被当风险计数 | `VideoSymbolResult.needs_review` 上抛；unknown **不计入** `has_symbol_risk` |
| `code_tracer.py` `trace_frame` 帧缺失 | `risk_level="safe"` | `risk_level="unknown", needs_review=True` |
| `code_tracer.py` `trace_frame` VLM 失败与"无代码"混判 | `not vlm_result or not has_code` 一律 safe | 拆开：`vlm_result is None` → unknown + needs_review；解析成功且 `has_code=False` 才是 safe |
| `code_tracer.py` `_vlm_analyze_code` JSON 解析失败 | 返回 `{"has_code": False}`（当"无代码"） | 返回 `None` |
| `code_tracer.py` `trace_video_frames` 聚合 | 无 `needs_review` | `VideoCodeTraceResult.needs_review` 上抛；unknown 不计入 `has_opensource_risk` |
| `pipeline.py` | 仅 map_auditor 贯通 `needs_review` | code_trace / symbol_detect 的 `needs_review` 同步置位并记入 `key_findings`；两分支异常时 `needs_review=True`（原仅打日志） |

## 四、遗留与边界

1. **API Key 是单密钥静态头**，满足"最小可用"；多租户/按用户配额需 JWT/OAuth（审计 17 C2 后续项）。密钥轮换 = 改环境变量重启。
2. **限流仍未做**（审计 10 提及的速率限制），鉴权挡住匿名后，持有 Key 的调用方仍可打满配额；建议随网关/中间件层补 `slowapi` 或前置 Nginx limit_req。
3. **`/api/v1/model-status` 等 Key 池状态端点**现在受鉴权保护（原来裸露），但持 Key 者仍可见脱敏后的池状态——已是日志脱敏后的字段，风险可接受。
4. `temporal_anomaly` 解析失败路径未显式置 `needs_review`（25 号文档 §4 已列）；其数据源是 dense_scan 的本地统计而非 VLM，失败面不同，本次未扩大范围。
5. 前端在配置 `API_KEY` 的生产环境需要调用方带头；当前前端未内置 Key 注入（本地开发不受影响）。若后续前端直连生产，需在部署层（Nginx 注入头或后端会话）解决，不建议把 Key 打进前端包。
6. 红线 76+ 的维度分抬升会改写 `d["score"]`（对齐 severity 与分数区间）；回测对比历史分数时需注意口径变化（R2 计量线已覆盖）。
