# VibeUtopia 仿真验证与基础迁移设计

## 文档定位
- 本文档在主线中的角色：回答"仿真比MVP更准吗"这一根本问题，验证仿真风控的可信度，完成数据库基础设施迁移，为后续趋势预测提供可信度基石
- 与"发前风控优先"的关系：验证优先于扩展——如果仿真不可信，预测就是空中楼阁；迁移服务于主线，不为迁移而迁移

## 本文档边界
- 本文档负责：回测框架设计、多轮一致性检查、可信度标注系统、数据库迁移（MySQL + SQLite双轨）、Go/No-Go判定标准、V2 vs MVP对比报告
- 本文档不负责：仿真引擎实现细节（见`08_仿真引擎设计.md`）、风险评估逻辑（见`09_分析决策层设计.md`）、前端展示（见`13_前端升级设计.md`）

## 对准确率的直接贡献
- 机制1：回测框架用历史事件验证仿真方向/平台/维度的预测准确率，5维加权量化V2 vs MVP改善
- 机制2：多轮一致性检查暴露仿真随机性，可信度标注让用户知晓结果置信区间
- 验证方式：回测用例覆盖5+历史事件，3轮一致性检查，准确率与一致性均达标方可Go

## 关键流程/结构
- 输入：历史事件种子文案 + 实际结果（BacktestCase）、当前仿真引擎
- 处理：种子文案分别经MVP静态评估和V2仿真增强评估 → 对比预测vs实际 → 量化改善 → 多轮一致性校验 → 可信度标注
- 输出：ComparisonReport（V2 vs MVP准确率对比）、ConsistencyReport（一致性报告）、CredibilityAnnotation（可信度标注）、数据库迁移就绪

## 依赖与降级
- 依赖：多模态API可用性、LLM API可用性、已有cases/reports历史数据、MySQL（可选）
- 失败降级策略：MySQL不可用时自动降级到SQLite（零依赖默认）；回测用例不足时先用3个最小集，后续补充；一致性为"低"时标注低置信度而非隐藏结果

## 验收标准
- 指标：回测方向准确率、V2 vs MVP提升幅度、多轮一致性等级
- 阈值：方向准确率>55%、V2比MVP提升>10% → Go；<55% → No-Go；55%-65% → Conditional Go
- 通过条件：回测5+用例，V2方向准确率>55%且提升>10%，一致性等级≥"中"

## 1. Go/No-Go 判定标准（与蓝图对齐）

> 验证优先于扩展。仿真可信度是后续一切预测功能的前提，Go/No-Go标准与蓝图阶段1验收直接挂钩。

| 判定 | 条件 | 后续动作 |
|------|------|---------|
| **Go** | 回测方向准确率>55%，且V2比MVP提升>10% | 可进入下一阶段（趋势预测等） |
| **Conditional Go** | 55% ≤ 准确率 < 65% | 可启动下一阶段，但需降低预测粒度，增加人工复检 |
| **No-Go** | 方向准确率<55% | 暂停后续扩展，先修仿真质量 |

> **核心原则**：No-Go不是失败，是止损。宁可多花时间修仿真质量，也不要在不稳定的基础上搭建预测。

## 2. 回测框架

### 2.1 设计思路

用已发生的历史热点事件作为测试用例，将事件发生前的信息（种子文案/新闻报道）输入仿真风控，看预测方向是否与实际结果一致。

### 2.2 回测用例来源

| 来源 | 说明 | 已有数据 |
|------|------|---------|
| cases/paperwork/ | 已有的9个真实案例文档 | 文案内容+风险分析报告 |
| cases/video_transcript/ | 4个B站视频转录 | 视频文案 |
| reports/analysis/ | 8个分析报告 | MVP分析结果 |
| tests/deep-analysis/ | 10个深度分析测试 | 更详细的分析 |
| 外部历史事件 | 补充3-5个已知舆论走向的事件 | 需手动整理 |

### 2.3 回测用例标准与库结构

**回测案例库目录结构**：
```
test_cases/
├── README.md                     # 案例库说明和标注规范
├── high_risk/                    # 高风险案例（实际翻车）
│   ├── case_001_党妹事件.yaml
│   ├── case_002_某博主辱女事件.yaml
│   └── ...
├── medium_risk/                  # 中风险案例（引发争议但未翻车）
│   └── ...
├── low_risk/                     # 低风险案例（安全内容）
│   └── ...
└── schema.yaml                   # 案例标注 Schema
```

### 2.4 回测流程

```
回测用例（种子文案 + 实际结果）
     │
     ▼
Step 1: 输入种子文案到仿真风控
  ├── MVP静态评估 → 预测A
  └── V2仿真增强评估 → 预测B
     │
     ▼
Step 2: 对比预测 vs 实际
  ├── 预测A vs 实际 → 准确率A
  └── 预测B vs 实际 → 准确率B
     │
     ▼
Step 3: 量化改善
  ├── 方向准确率: V2 vs MVP
  ├── 平台预测准确率: V2 vs MVP
  └── 风险维度准确率: V2 vs MVP
     │
     ▼
Step 4: 生成回测报告 → Go/No-Go判定
```

### 2.5 准确率评估维度（5维加权）

| 维度 | 定义 | 权重 |
|------|------|------|
| **方向准确率** | 舆论热度方向(上涨/持平/下降)预测正确 | 40% |
| **平台准确率** | 预测波及的平台与实际一致 | 20% |
| **维度准确率** | 预测的风险维度与实际一致 | 20% |
| **群体准确率** | 预测的受影响群体与实际一致 | 10% |
| **极化准确率** | 是否出现极化的预测正确 | 10% |

> 加权准确率 = Σ(维度准确率 × 权重)。方向准确率权重最高（40%），因为方向是"发前风控"最关键的判断。

## 3. 多轮一致性检查

### 3.1 设计思路

同一事件运行3次仿真，评估结果是否稳定。如果3次结果各不相同，说明仿真随机性太大，不可信。

### 3.2 一致性检查实现

```python
class ConsistencyChecker:
    """多轮一致性检查器"""

    async def check(self, seed_content: str, rounds: int = 3) -> ConsistencyReport:
        """运行多轮仿真，检查一致性"""

        results = []
        for i in range(rounds):
            result = await self.simulation_engine.run_lightweight(seed_content)
            results.append(result)

        # 评估方向一致性
        directions = [r.overall_direction for r in results]
        direction_consistency = self._calc_agreement(directions)

        # 评估平台反应一致性
        platform_consistency = self._calc_platform_agreement(results)

        # 评估风险维度一致性
        risk_consistency = self._calc_risk_agreement(results)

        return ConsistencyReport(
            rounds=rounds,
            direction_consistency=direction_consistency,  # 3/3=1.0, 2/3=0.67, 1/3=0.33
            platform_consistency=platform_consistency,
            risk_consistency=risk_consistency,
            overall_consistency=(direction_consistency * 0.5 +
                                platform_consistency * 0.25 +
                                risk_consistency * 0.25),
            verdict="high" if direction_consistency >= 1.0
                    else "medium" if direction_consistency >= 0.67
                    else "low"
        )
```

### 3.3 一致性标准

| 等级 | 方向一致性 | 含义 | 处理方式 |
|------|-----------|------|---------|
| 高 | 3/3一致 | 仿真稳定，结果可信 | 标注高置信度 |
| 中 | 2/3一致 | 仿真有随机性，需标注不确定性 | 标注中置信度，提示用户 |
| 低 | 1/3或0/3 | 仿真不稳定，不可用于预测 | 标注低置信度，不建议作为决策依据 |

## 4. 可信度标注系统

### 4.1 标注格式

在每个风控报告中标注可信度信息：

```python
@dataclass
class CredibilityAnnotation:
    """可信度标注"""
    method: str                    # static / signal_enhanced / simulation_enhanced
    confidence: float              # 整体置信度 0-1
    simulation_rounds: int         # 仿真轮次（仅仿真模式）
    direction_consistency: float   # 方向一致性
    uncertainty_sources: List[str] # 不确定性来源
    data_freshness: str            # 数据新鲜度（信号采集时间）

    # 不确定性来源枚举
    UNCERTAINTY_SOURCES = [
        "LLM生成随机性",
        "Agent数量有限(100个)",
        "仿真时长有限(6小时)",
        "当前热点数据可能有延迟",
        "知识图谱实体覆盖不完整",
    ]
```

### 4.2 置信度计算

```python
def calc_confidence(method, consistency, data_freshness):
    """计算置信度"""

    if method == "static":
        return 0.5  # MVP静态评估，置信度基准

    elif method == "signal_enhanced":
        base = 0.6  # 信号增强，比静态更准
        if data_freshness < "1h": base += 0.1
        elif data_freshness > "24h": base -= 0.1
        return min(base, 0.8)

    elif method == "simulation_enhanced":
        base = 0.5
        if consistency == "high": base = 0.75
        elif consistency == "medium": base = 0.6
        elif consistency == "low": base = 0.4
        return min(base, 0.85)
```

> 可信度标注不是装饰，是用户决策的依据。低置信度结果必须明确标注，而非隐藏。

## 5. 数据库迁移：MySQL + SQLite 双轨

### 5.1 设计原则

- **SQLite 是默认、零依赖选项**：单用户场景无需任何额外安装
- **MySQL 用于多用户/高并发场景**：团队部署、API服务化时启用
- **通过环境变量一键切换**：代码无需修改，配置即切换

### 5.2 迁移范围

| 数据 | 当前存储 | 迁移目标 | 优先级 |
|------|---------|---------|--------|
| 风控任务+结果 | SQLite(tasks/risk_items/platform_reactions) | MySQL + SQLite降级 | P0 |
| 分析摘要 | SQLite(analysis_summaries) | MySQL + SQLite降级 | P0 |
| 仿真轨迹 | SQLite(simulation_records/traces) | MySQL + SQLite降级 | P1 |
| 热点关联/实体风险链 | SQLite(新表) | MySQL + SQLite降级 | P0 |
| 向量检索 | - | ChromaDB（内嵌式，零部署） | P1 |
| 信号事件 | SQLite + Neo4j | MySQL/SQLite + Neo4j | P2 |
| 博主数据 | 无 | MySQL/SQLite(新表) | P3(阶段6用) |

### 5.3 数据库配置

```python
# database.py — 统一数据库入口

DATABASE_URL = os.getenv("DATABASE_URL") or "sqlite:///./vibeutopia.db"

def get_engine():
    """根据配置自动选择数据库引擎"""
    db_url = DATABASE_URL
    if db_url.startswith("mysql"):
        # MySQL模式：多用户/高并发
        return create_engine(db_url, pool_size=10, max_overflow=20)
    else:
        # SQLite模式：单用户/零依赖（默认）
        return create_engine(db_url)
```

> **关键变更**：默认从 `sqlite:///./data/vibeutopia.db` 改为 `sqlite:///./vibeutopia.db`（根目录，简化路径）。MySQL不再是唯一迁移目标，而是高并发场景的可选升级。

### 5.4 迁移策略

```python
# 迁移步骤：

# Step 1: 更新 database.py，支持 MySQL + SQLite 双轨
# - SQLite 为默认（零依赖）
# - MySQL 为可选升级（环境变量启用）
# - 所有模型定义兼容两种数据库

# Step 2: 更新所有模型
# - 确保所有 Column 定义兼容 MySQL
# - String → 需要指定长度（MySQL要求）
# - Text → MySQL的LONGTEXT

# - 读取 SQLite 数据

# - 重启服务
# - 保留 SQLite 文件作为备份
```

## 8. 实现优先级

| 优先级 | 模块 | 理由 | 前置依赖 |
|--------|------|------|---------|
| P0 | 回测用例整理 | 从cases/reports中提取5个标准回测用例 | 无 |
| P0 | 回测框架 | 核心验证能力，回答"仿真更准吗" | 回测用例 |
| P0 | Go/No-Go判定 | 与蓝图验收对齐的决策机制 | 回测结果 |
| P0 | 数据库双轨迁移 | SQLite默认+MySQL可选，基础设施越早越安全 | 无 |
| P1 | 多轮一致性检查 | 验证仿真稳定性 | 回测框架 |
| P1 | 可信度标注 | 用户需要知道结果可信度 | 一致性检查 |
| P2 | V2 vs MVP对比报告 | 量化改善，非阻塞 | 回测框架+一致性检查 |
| P2 | ChromaDB接入 | 向量检索基础设施，为阶段3-5准备 | 无 |

> **注意**：验证（P0）优先于迁移（P0但可延迟），迁移服务于主线。如果回测No-Go，优先修仿真质量而非推进迁移。
