# 性能与数据指标体系报告

> 审计范围：VibeUtopia 全链路（信号采集 → 多模态分析 → Agent 仿真 → 风险报告）
> 数据来源：`docs/reports/` 验收报告、`data/` 日志与回测数据、`tests/large_scale_test_results/`、`src/backend/services/` 实现、`docs/design/` 与 `docs/guides/` 规格
> 基准日期：2026-05（日志与测试数据时间戳）；本报告为现状审计与指标体系设计，不含未验证的推断值

## 1. 执行摘要

**总体判断**：系统已具备完整的功能链路与初步的性能约束（LLM 分层、断点续传、限流冷却、仿真规模分级），但**成本/延迟/质量三类数据均未形成闭环可观测**，大量"性能数字"停留在设计目标或模拟演示，缺少真实链路的 P95 分布与按次成本账单。

| 维度 | 现状 | 关键证据 | 风险等级 |
|------|------|----------|----------|
| 分析耗时 | 有设计基准，无实测分位 | 运维手册 Lite-Ultra 表为"参考值" | P1 |
| LLM 成本 | 有估算模型，无计量账单 | ScaleManager 估算 ¥0.5–50/次；无 token 落库 | P0 |
| 回测准确率 | 有 A/B 结果，受 429 污染 | +17.6%（36 案例）；另一轮 56% 因 40% 案例 0 分 | P1 |
| 429/配额 | 冷却机制已有，但双 Key 同时耗尽 | `t7_enhancement.log` 双 Key 冷却 300s | P0 |
| 断点续传 | 8 阶段检查点已实现 | `resumable_analyzer.py`；无端到端恢复实测 | P2 |
| 前端渲染 | 无虚拟列表/节流实现 | 前端源码检索无 throttle/virtual 命中 | P2 |
| 可观测性 | 关键指标不可度量 | 无 token 计量、无延迟分位、无成本报表 | P0 |

**一句话结论**：先补「计量」（每次分析的 token/耗时/阶段/成功率落库），再谈「优化」；否则任何性能优化都无法证明收益。

## 3. 性能瓶颈与根因

### 3.1 长视频 30+ 分钟（P1）
- **现象**：素材已达 48–162MB / 预估 10–30 分钟时长；设计目标「细粒度增量 ≤30s/10 分钟」；运维基准 120–300s（Lite）显然只覆盖短视频。
- **根因**：帧提取（delta 模式阈值 5%、I 帧 30s、SSIM 0.95 去重）随视频长度线性增长；细粒度密集扫描 `dense_fps=1.0` 且 `max_analysis_frames=50` 是硬顶，长视频实际是**抽样而非全量**，精度-耗时权衡未量化。
- **缺口**：无按视频时长分桶的耗时/成本曲线。

### 3.2 API 429 / 配额耗尽（P0）
- **现象**：`t7_enhancement.log` 中 longcat Key1/Key2 同时 429（"服务端模型可用容量超过限制"），冷却 300s；deepseek 全系 401；阶段 2.4 回测 40% 案例因此得 0 分。
- **根因**：`llm_client.py` 冷却以 `provider:model_id:key_index` 为粒度（双 Key 可独立冷却，机制正确），但**缺少跨请求的全局并发闸门与配额预算**——并行阶段（Phase 2.6/2.7 `asyncio.gather`）+ 仿真多平台并发会在瞬间打爆限速窗口；401（Key 失效）未与 429 区分处置，白白重试 3 次。
- **放大效应**：一次逻辑调用最多 4 模型 × 3 重试 = 12 次 HTTP，浪费限流配额。

### 3.3 断点续传（P2，能力已备但未验收）
- **已实现**：`resumable_analyzer.py` 8 阶段检查点 + `checkpoint_manager.py` 帧级恢复单元 + 429 时 `mark_interrupted` 保存状态 + `verify_video_unchanged` 校验 + `quota_exhausted_count` 递增等待重试。
- **缺口**：无「长视频中断→恢复→成本节省 %」的实测数据；`routes_resume.py` 存在但无测试覆盖记录；检查点文件落盘策略（原子性、清理）未见规格。

### 3.4 并行优化残留（P2）
- `enhanced_analyzer.py`：Phase 2.6 多模态与 Phase 2.7 细粒度已 `asyncio.gather` 并行。
- `video_config.yaml`：`max_concurrent_vlm=3`（帧序列/OCR/画面风险各自为 3），**总并发上限无全局协调**，三路并行时实际 VLM 并发可到 9，与 429 风险叠加。
- 批量链路：`batch_analyzer.py` 有 Semaphore + LRU 缓存（`llm_calls_saved` 计数），但缓存命中率无接口暴露（PHASE5 列了 `/api/v3/batch/cache-stats`，数据未入日志）。

### 3.5 前端大数据渲染（P2）
- 前端组件含 `KnowledgeGraph.vue`（D3 力导向）、`SignalPanel.vue`（热榜+事件时间线）、`PolarizationChart.vue`、`EntityRiskTimeline.vue`；产物中 `d3-*.js` 与 `echarts-*.js` 为独立 chunk。
- **源码检索无虚拟列表 / throttle / debounce / requestAnimationFrame 节流实现**。
- 数据面：单轮 254 条热榜 + 188 事件簇 + 图谱实体边，若全量进 D3 力导向与 ECharts，首屏与交互帧率存在明确风险。
- `dist/assets/index-*.js` 与 `Workbench-*.js` 体积未见分包预算记录。

### 3.6 环境/工程噪音污染指标（P1）
- 大规模实际执行 36 案例全挂：`/workspace/backend/prompts/risk_assessment_v2.txt` 路径硬编码/环境不一致。
- 日志编码损坏（GBK/UTF-8 混用），`signal_collection.log` / `t7_enhancement.log` 中文乱码，无法直接做文本挖掘。
- `tests/large_scale_test_results` 中 83% 准确率来自「模拟数据演示」，若被引用为产品指标会严重误导。

1. 无法回答「本周总 token / 总花费」——`llm_client` 仅内存级 `_key_usage_stats`（calls/errors/last_used），**不落库、不计 token、不计费**。

3. 无法回答「429 重试浪费了多少配额」——重试次数无独立指标（checkpoint 有 `llm_calls_failed` 字段但无报表）。
4. 无法回答「缓存省了多少」——`llm_calls_saved` 有计数无导出。

## 5. 产品指标体系设计（北极星 + 分层指标）

### 5.1 北极星指标

**周活跃创作者的「有效风险拦截数」**（Effective Risk Blocks / ERB）

> 定义：一周内，创作者经系统预警后**确认规避的高风险事件数**（含：改写后降级成功 + 主动放弃发布 + 报告命中后人工复核确认为真风险）。
>
> 为什么是它：对齐「发前风控优先」的产品使命；同时驱动留存（有用才回来）、付费（避免的损失可货币化）、算法迭代（漏报直接减少 ERB）。

辅助北极星（同一口径树下）：
- **风险避免价值额（¥）**：拦截事件 × 行业单次翻车损失基准（舆情/广告下架/平台处罚的粗估单价表）
- **漏报率红线**：红线维度（政治敏感/法律合规/民族宗教/事实错误/平台禁区）漏报次数，**目标恒为 0，作为否决项**

### 5.2 创作者价值指标（AARRR 中 Activation/Retention 的价值面）

| 指标 | 定义 | 初始目标 | 度量方式 |
|------|------|----------|----------|
| 首报价值达成率 | 新用户 7 天内完成≥1 次「可行动报告」 | ≥40% | 任务完成埋点 |
| **改写采纳率** | 报告建议句被创作者采纳（改写/删除）的比例 | ≥30% | 改写前后 diff + 用户确认动作 |
| 报告可操作率 | 报告含≥1 条具体修改建议的比例 | ≥90% | 报告结构检查 |
| 风险避免确认率 | 用户标记「已规避」的预警数 / 总有效预警 | ≥50% | 用户反馈闭环 |
| 误报打扰率 | 用户标「不相关/误报」比例 | ≤15% | 报告级反馈 |
| 二次使用间隔 | 首次分析到再次分析的中位天数 | ≤7 天 | 行为日志 |

### 5.3 算法指标（准确/召回/校准）

| 指标 | 定义 | 当前实测 | 目标 |
|------|------|----------|------|
| 风险等级准确率 | 与人工标注一致 | 77–82%（无干扰） | ≥85% |
| 高风险召回率（漏报的补） | Red 样本召回 | 85.6%（A 组）/ 红分级 88.5% | ≥92% |
| 误报率 | Green 被判 Red 的比例 | 实测缺失 | ≤8% |
| F1-Score | 调和平均 | 82.2%（A 组） | ≥0.85 |
| 红线维度命中率 | 五红线维命中 | 83.4–92.1% | 全部 ≥90% |
| **校准度 ECE** | 置信度与实际正确率的偏差 | **未度量** | ECE ≤ 0.05 |
| 3 轮一致性 | 方向40%+分数30%+维度30% | 机制已有（>60% 门槛） | ≥75% |
| 可信度标注覆盖率 | 输出含高/中/低可信标注 | 机制已有 | 100% |
| 模拟-真实偏差 | 模拟演示 83% vs 真实链路波动 | 已知偏差 | 差异 <5pt 且可解释 |

**度量纪律**：准确率统计必须标注「环境完整性」（配额充足 / 路径正确 / 真实 LLM），剔除 0 分无效样本后单独报告 `valid_accuracy` 与 `valid_ratio` 两个指标，避免阶段 2.4 的 56% 污染算法结论。

### 5.4 工程指标（延迟/成功率/成本）

| 指标 | 口径 | 初始目标 |
|------|------|----------|

| 用户行为（采纳/反馈） | — | **不存在** | ❌ |

### 7.2 落地路线（三步）

**第 1 步：计量层（2 周内，P0）**
1. `LLMUsageMeter`：每次调用落库 `{task_id, stage, model, prompt_tokens, completion_tokens, latency_ms, status, retry_of, cost_cny}`（单价表进 `model_config.yaml`）。
2. `StageTimer`：8 阶段耗时写入 checkpoint 并汇总到 `data/reports/perf_*.jsonl`。
3. 结构化日志（JSON lines，UTF-8 强制），替换乱码文本日志。
4. 任务完成事件单行 JSON：`{task_id, modality, duration_s, llm_calls, tokens, cost, stages[], outcome}`。

**第 2 步：聚合与告警（第 3–4 周）**
1. 日聚合报表：延迟分位、成功率、429 率、成本/次、valid_accuracy 与 valid_ratio。
2. 告警规则对齐 §6 SLI；429 率与红线漏报进 P0 通道。
3. `/api/v3/metrics/summary` 与 `/api/v3/metrics/timeseries`，供前端仪表盘（可复用 ECharts chunk）。

**第 3 步：产品指标闭环（第 5–8 周）**
1. 报告反馈埋点（采纳/误报/已规避），回流 `改写采纳率` 与 `ERB`。
2. 前端 `PerformanceObserver`（LCP/INP）+ 图谱渲染 FPS 采样。
3. 回测集版本化 + 校准曲线（ECE）计算脚本，纳入回归门禁。
4. 月度成本与质量报告模板，口径与 ScaleManager 估算器统一。

### 7.3 目录与保留建议
- `data/metrics/`：jsonl 原始计量（保留 90 天）
- `data/metrics/agg/`：日/周聚合（永久）
- 日志轮转 14 天；敏感字段（Key）脱敏——**当前日志与 MEMORY 中存在明文 Key，属 P0 安全项，需立刻轮换并移出仓库**。
