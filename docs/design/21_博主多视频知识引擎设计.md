# VibeUtopia 博主多视频知识引擎设计

> 基于 VideoRAG (港大×百度, arXiv:2502.01549) 核心思想，为博主个人服务场景设计的多视频理解与知识检索引擎
>
> ✅ 蓝图已确认，进入实施阶段
>
> **确认决策**：VLM=Qwen-VL-Max(API) | 多模态编码=Chinese-CLIP | GPU模式=API模式 | 实施=3步走

## 文档定位
- 本文档在主线中的角色：将博主服务从"单视频风控"升级为"全视频知识引擎"，实现博主全部视频的深度理解、跨视频推理与精准内容检索
- 与现有模块的关系：复用 graph/（知识图谱）、multimodal_analyzer（多模态）、video_extractor（视频提取）、llm_client（LLM调度），新增双通道索引与混合检索
- 参考论文：VideoRAG: Retrieval-Augmented Generation with Extreme Long-Context Videos (Xubin Ren, Lingrui Xu et al., 2025)

## 本文档边界
- 本文档负责：博主多视频知识引擎的架构设计、模块划分、数据流、实施路径
- 本文档不负责：前端页面设计（复用现有工作台）、具体代码实现（确认后另开任务）
- 显式排除：不替代现有风控流程，而是在风控基础上增加博主知识服务层

## 对准确率的直接贡献
- 当前贡献：**间接提升**——跨视频知识关联可发现单视频无法识别的风险模式（如博主在多个视频中逐步触碰风险边界）
- 潜在贡献：博主知识画像 → 个性化风险阈值 → 更精准的风控判断

## 1. 设计理念

### 1.1 核心问题

博主个人服务的核心场景：**一个博主可能有数十到数百个视频，总时长从几十到数百小时**。用户需要：

| 需求 | 示例 | 现有能力 | 差距 |
|------|------|---------|------|
| 跨视频问答 | "这个博主对AI取代人类的看法是什么？" | ❌ 只能单视频分析 | 需要跨视频知识整合 |
| 内容检索 | "找出博主所有提到'内卷'的视频片段" | ❌ 无检索能力 | 需要语义检索 |
| 风格画像 | "这个博主的叙事风格是什么？" | ⚠️ blogger_history只做风险画像 | 需要全维度画像 |
| 知识关联 | "博主在视频A和视频B中对同一话题的观点是否矛盾？" | ❌ 无跨视频关联 | 需要知识图谱 |
| 增量更新 | "博主发了新视频，能自动更新知识库吗？" | ❌ 需要重新分析 | 需要增量索引 |

### 1.2 VideoRAG 核心思想借鉴

VideoRAG 的三个核心创新点，恰好解决上述问题：

1. **双通道多模态知识索引**
   - 通道1：图基文本知识对齐 → 跨视频语义关系建模
   - 通道2：多模态上下文编码 → 视觉特征保留与检索

2. **增量式知识图谱构建**
   - 新视频无需重建索引，自动扩展知识图谱
   - 实体对齐合并，保证跨视频一致性

3. **混合多模态检索**
   - 文本检索 + 视觉检索自适应融合
   - 查询驱动的精准内容定位

### 1.3 设计原则

- **复用优先**：复用 VibeUtopia 已有的 graph/、multimodal/、video_extractor/ 模块，不重复造轮子
- **中文优先**：ASR 用阿里 Paraformer（已有），VLM 用 Qwen-VL，LLM 用 DeepSeek-V3（已有调度）
- **渐进增强**：分3步实施，每步都有可验证的交付物
- **成本可控**：单卡 RTX 3090/4090 可运行，LLM 调用复用现有厂商调度

## 3. 模块设计

### 3.1 新增模块

#### 3.1.1 `blogger_video_indexer.py` — 博主视频批量索引服务

**职责**：管理博主视频的批量导入、增量索引、知识图谱构建

```python
class BloggerVideoIndexer:
    """博主视频批量索引器"""

    async def index_blogger(self, blogger_id: str, video_paths: List[str]) -> IndexResult:
        """为博主建立全视频知识索引"""
        # 1. 视频切分 + 多模态提取
        # 2. VLM视觉描述生成
        # 3. ASR转录 + OCR
        # 4. LLM实体关系抽取 → 知识图谱增量构建
        # 5. 视觉嵌入编码存储
        # 6. 跨视频实体对齐合并

    async def incremental_index(self, blogger_id: str, new_video_paths: List[str]) -> IndexResult:
        """增量索引新视频（不重建已有索引）"""
        # 1. 检查已索引视频，跳过重复
        # 2. 对新视频执行完整索引流程
        # 3. 实体对齐：新实体与已有图谱合并
        # 4. 更新视觉嵌入库

    def get_index_status(self, blogger_id: str) -> IndexStatus:
        """获取博主索引状态（已索引视频数、实体数、关系数等）"""
```

class VideoEmbeddingStore:

#### 3.1.3 `hybrid_retriever.py` — 混合多模态检索器

**职责**：融合文本检索和视觉检索，自适应选择最优检索策略

```python
class HybridRetriever:
    """混合多模态检索器（VideoRAG核心检索逻辑）"""

    async def retrieve(self, query: str, blogger_id: str, mode: str = "auto") -> RetrievalResult:
        """混合检索：文本通道 + 视觉通道 → 自适应融合

        mode:
        - "text": 仅文本检索（知识图谱 + 文本嵌入）
        - "visual": 仅视觉检索（多模态嵌入）
        - "auto": 自适应融合（默认）
        """

    def _text_retrieval(self, query: str, blogger_id: str) -> List[TextMatch]:
        """文本检索通道：知识图谱遍历 + 文本嵌入相似度"""

    def _visual_retrieval(self, query: str, blogger_id: str) -> List[VisualMatch]:
        """视觉检索通道：多模态嵌入相似度"""

    def _adaptive_fusion(self, text_results, visual_results, query) -> List[FusedMatch]:
        """自适应融合：根据查询类型调整文本/视觉权重"""
```

## 4. 技术选型

### 4.1 与 VideoRAG 的选型对比

| 组件 | VideoRAG 默认 | VibeUtopia 选型 | 选型理由 |
|------|-------------|----------------|---------|
| **ASR** | faster-whisper (英文) | **阿里 Paraformer-v2** (已有) | 中文识别更准，支持说话人分离+时间戳 |
| **VLM** | MiniCPM-V-2_6-int4 (本地) | **Qwen-VL-Max** (API) 或 **InternVL2** (本地) | 中文视觉理解更强，API模式无需本地GPU |
| **LLM** | GPT-4o-mini | **DeepSeek-V3** (已有调度) | 中文推理更强，已有多厂商智能调度 |
| **Embedding** | OpenAI text-embedding | **BGE-M3** (本地) 或 **text-embedding-v3** (API) | 中文语义嵌入更好 |
| **多模态编码** | ImageBind | **CLIP (ViT-L/14)** 或 **ImageBind** | CLIP中文适配更好，ImageBind支持更多模态 |
| **知识图谱** | Neo4j / NetworkX | **Neo4j** (已有) | 已有完善的Neo4j+降级模式 |
| **向量库** | HNSWLib / NanoVectorDB | **ChromaDB** (已有) + **NanoVectorDB** (新增) | ChromaDB已部署，NanoVectorDB轻量补充 |
| **LLM调度** | OpenAI API 直连 | **llm_client** (已有多厂商调度) | 已有6厂商智能切换+配额管理 |

### 4.2 GPU 需求

| 模式 | GPU需求 | 说明 |
|------|---------|------|
| **API模式** (推荐) | 无需GPU | VLM/LLM/Embedding全走API，仅ASR可能需本地 |
| **混合模式** | RTX 3090 (24GB) | ASR本地 + Embedding本地，VLM/LLM走API |
| **全本地模式** | RTX 4090 (24GB) | 所有模型本地运行，适合隐私敏感场景 |

## 5. 实施路径（3步走）

### 第1步：视频知识索引增强

**目标**：让系统能从博主视频中提取结构化知识并构建知识图谱

**交付物**：
- [ ] `blogger_video_indexer.py`：博主视频批量索引服务
- [ ] `entity_extractor.py` 增强：增加视频维度实体类型和关系类型
- [ ] `graph_updater.py` 增强：增加跨视频实体对齐合并
- [ ] `multimodal_analyzer.py` 增强：增加VLM视觉描述生成
- [ ] VLM 接入：Qwen-VL-Max API 或 InternVL2 本地

**复用率**：~80%（graph_store、entity_extractor、graph_updater、llm_client、keyframe_extractor、audio_transcriber 全部复用）

**验收标准**：
1. 给定3个博主视频（总时长≥1小时），能自动构建知识图谱
2. 知识图谱包含≥20个实体和≥15个关系
3. 跨视频实体对齐合并正确率≥80%（人工抽样10个实体）
4. 增量索引：新增1个视频后，图谱正确扩展，不丢失已有知识

### 第2步：双通道检索

**目标**：实现文本+视觉双通道检索，支持博主知识问答

**交付物**：
- [ ] `video_embedding_store.py`：视觉嵌入存储
- [ ] `hybrid_retriever.py`：混合多模态检索器
- [ ] `blogger_knowledge_service.py`：博主知识问答服务
- [ ] Embedding 模型接入：BGE-M3 或 text-embedding-v3
- [ ] 多模态编码接入：CLIP 或 ImageBind

**复用率**：~50%（新增核心检索逻辑，复用 graph_store 的子图查询和 llm_client 的回答生成）

**验收标准**：
1. 给定5个博主视频（总时长≥3小时），能回答5个跨视频问题，准确率≥70%
2. 内容检索："找出博主提到XX的所有片段" → 返回结果准确率≥80%
3. 混合检索 vs 纯文本检索：在需要视觉理解的问题上，混合检索准确率提升≥15%
4. 单次问答响应时间≤10秒（不含索引构建时间）

## 7. 数据模型

### 7.1 新增数据模型

```python
@dataclass
class VideoSegment:
    """视频片段"""
    segment_id: str
    video_path: str
    blogger_id: str
    start_time: float              # 起始时间(秒)
    end_time: float                # 结束时间(秒)
    frame_paths: List[str]         # 采样帧路径
    visual_description: str        # VLM生成的视觉描述
    asr_text: str                  # ASR转录文本
    ocr_text: str                  # OCR提取文本
    combined_text: str             # 合并文本知识
    embedding: Optional[List[float]] = None  # 视觉嵌入向量

@dataclass
class BloggerKnowledgeProfile:
    """博主全知识画像（扩展BloggerHistory的RiskProfile）"""
    blogger_id: str
    platform: str

    # 风格维度
    narrative_style: str           # 叙事风格
    expression_style: str          # 表达风格
    vocabulary_profile: dict       # 词汇偏好

    # 观点维度
    core_viewpoints: List[dict]    # 核心观点列表
    topic_stances: Dict[str, str]  # 话题立场映射
    contradictions: List[dict]     # 观点矛盾

    # 话题维度
    primary_topics: List[str]      # 主要话题
    topic_distribution: Dict[str, float]  # 话题分布
    topic_evolution: List[dict]    # 话题演变

    # 受众维度
    estimated_audience: dict       # 推测受众画像

    # 风险维度（复用blogger_history）
    risk_profile: dict             # 风险画像

    # 元信息
    total_videos: int              # 已索引视频数
    total_duration: float          # 总时长(小时)
    knowledge_graph_stats: dict    # 知识图谱统计
    last_updated: str              # 最后更新时间

@dataclass
class IndexResult:
    """索引结果"""
    blogger_id: str
    videos_indexed: int
    segments_created: int
    entities_extracted: int
    relations_extracted: int
    entities_merged: int           # 跨视频合并的实体数
    duration_seconds: float        # 索引耗时

@dataclass
class AnswerResult:
    """问答结果"""
    question: str
    answer: str
    references: List[dict]         # 引用的视频片段（含时间戳）
    confidence: float              # 置信度
    retrieval_mode: str            # 使用的检索模式
```

### 7.2 知识图谱 Schema 扩展

在现有 Neo4j 图谱中新增以下节点和边类型：

**新增节点标签**：
- `VideoSegment`：视频片段节点，属性包含时间戳、视频来源、文本摘要
- `Topic`：话题节点，属性包含话题名称、出现频次、情感倾向
- `Viewpoint`：观点节点，属性包含观点内容、置信度、首次出现时间

**新增边类型**：
- `MENTIONS`：实体/片段 → 话题（提及）
- `HOLDS_VIEW`：片段 → 观点（持有观点）
- `CONTRADICTS`：观点 → 观点（矛盾）
- `SUPPORTS`：观点 → 观点（支撑）
- `EVOLVED_FROM`：观点 → 观点（演变）
- `APPEARS_IN`：实体 → 视频片段（出现）

## 9. 风险与缓解

| 风险 | 概率 | 影响 | 缓解策略 |
|------|------|------|---------|
| VLM API 成本高 | 中 | 中 | 支持本地模型降级(InternVL2)；长视频可降低采样率 |
| 实体对齐错误合并 | 中 | 高 | 人工抽检验证；设置相似度阈值；提供合并回退机制 |
| 大量视频索引耗时长 | 高 | 中 | 异步索引+进度通知；支持断点续索引 |
| ImageBind/CLIP 中文效果差 | 中 | 中 | 优先使用中文适配的CLIP模型(Chinese-CLIP) |
| 知识图谱过大影响查询 | 低 | 中 | 按博主分区存储；定期清理低质量实体 |
