## 监控方案

### 健康检查端点

| 端点 | 说明 | 检查内容 |
|------|------|----------|
| `GET /api/v1/models` | 模型可用性 | 硬件层级、模型状态 |
| `GET /api/v3/hardware-info` | 硬件状态 | GPU、CPU、内存 |
| `GET /api/v3/model-status` | Key 池状态 | API Key 可用性 |
| `GET /api/v3/graph/overview` | 图谱状态 | Neo4j 连接、节点/边数 |
| `GET /api/v1/memory/status` | 记忆存储状态 | ChromaDB 可用性、记忆数量 |
| `GET /api/v3/signals/scheduler/status` | 调度器状态 | 采集是否运行 |

### 健康检查脚本

```bash
#!/bin/bash
# health_check.sh - VibeUtopia 健康检查

API_BASE="http://localhost:8000"
ALERT=""

# 检查后端服务
HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" "$API_BASE/api/v1/models")
if [ "$HTTP_CODE" != "200" ]; then
  ALERT="$ALERT\n[CRITICAL] 后端服务不可用 (HTTP $HTTP_CODE)"
fi

# 检查模型状态
MODELS=$(curl -s "$API_BASE/api/v3/model-status" 2>/dev/null)
KEY_COUNT=$(echo "$MODELS" | python3 -c "import sys,json; d=json.load(sys.stdin); print(len(d.get('key_pool',{})))" 2>/dev/null)
if [ "$KEY_COUNT" = "0" ] || [ -z "$KEY_COUNT" ]; then
  ALERT="$ALERT\n[WARNING] 无可用 API Key"
fi

# 检查图谱状态
GRAPH=$(curl -s "$API_BASE/api/v3/graph/overview" 2>/dev/null)
CONNECTED=$(echo "$GRAPH" | python3 -c "import sys,json; print(json.load(sys.stdin).get('connected',False))" 2>/dev/null)
if [ "$CONNECTED" = "False" ]; then
  ALERT="$ALERT\n[WARNING] Neo4j 不可用，运行在降级模式"
fi

# 检查 ChromaDB
MEMORY=$(curl -s "$API_BASE/api/v1/memory/status" 2>/dev/null)
CHROMA=$(echo "$MEMORY" | python3 -c "import sys,json; print(json.load(sys.stdin).get('chromadb_available',False))" 2>/dev/null)
if [ "$CHROMA" = "False" ]; then
  ALERT="$ALERT\n[WARNING] ChromaDB 不可用"
fi

if [ -z "$ALERT" ]; then
  echo "[OK] 所有服务正常"
else
  echo -e "$ALERT"
fi
```

## 备份策略

### 数据库备份

#### MySQL 备份

```bash
#!/bin/bash
# backup_mysql.sh

BACKUP_DIR="/backup/mysql"
DATE=$(date +%Y%m%d_%H%M%S)
MYSQL_CONTAINER="vibeutopia-mysql"

mkdir -p $BACKUP_DIR

# 全量备份
docker exec $MYSQL_CONTAINER mysqldump -u vibe_user -pvibe_password \
  --single-transaction --routines --triggers vibeutopia \
  | gzip > "$BACKUP_DIR/vibeutopia_$DATE.sql.gz"

# 保留最近 30 天的备份
find $BACKUP_DIR -name "*.sql.gz" -mtime +30 -delete

echo "MySQL 备份完成: vibeutopia_$DATE.sql.gz"
```

#### SQLite 备份

```bash
#!/bin/bash
# backup_sqlite.sh

BACKUP_DIR="/backup/sqlite"
DATE=$(date +%Y%m%d_%H%M%S)
DB_PATH="./data/vibeutopia.db"

mkdir -p $BACKUP_DIR

# SQLite 安全备份（使用 .backup 命令）
sqlite3 "$DB_PATH" ".backup '$BACKUP_DIR/vibeutopia_$DATE.db'"

# 压缩
gzip "$BACKUP_DIR/vibeutopia_$DATE.db"

# 保留最近 30 天
find $BACKUP_DIR -name "*.db.gz" -mtime +30 -delete

echo "SQLite 备份完成: vibeutopia_$DATE.db.gz"
```

### Neo4j 备份

```bash
#!/bin/bash
# backup_neo4j.sh

BACKUP_DIR="/backup/neo4j"
DATE=$(date +%Y%m%d_%H%M%S)
NEO4J_CONTAINER="vibeutopia-neo4j"

mkdir -p $BACKUP_DIR

# Neo4j 在线备份
docker exec $NEO4J_CONTAINER neo4j-admin database dump neo4j \
  --to-path=/backups/

# 压缩
gzip "$BACKUP_DIR/neo4j_$DATE.dump"

# 保留最近 30 天
find $BACKUP_DIR -name "*.dump.gz" -mtime +30 -delete

echo "Neo4j 备份完成: neo4j_$DATE.dump.gz"
```

## 扩容方案

### 垂直扩容

#### 增加计算资源

| 资源 | 扩容方式 | 影响 |
|------|----------|------|
| CPU | 升级到更多核心 | 提升并发处理能力 |
| 内存 | 增加到 32GB+ | 支持更多 Agent 仿真 |
| GPU | 升级到更大 VRAM | 支持本地大模型推理 |
| 磁盘 | 扩展到 SSD | 提升数据库和 ChromaDB 性能 |

#### GPU 升级建议

| 当前 GPU | 推荐升级 | 效果 |
|----------|----------|------|
| 无 GPU | RTX 4060 (8GB) | 可运行 7B 量化模型 |
| RTX 4060 | RTX 4070 Ti (12GB) | 可运行 14B 量化模型 |
| RTX 4070 Ti | RTX 4090 (24GB) | 可运行 32B 模型 |
| RTX 4090 | A100 (80GB) | 可运行 72B 模型 |

### 水平扩容

#### 后端多实例

```nginx
# Nginx 负载均衡配置
upstream vibeutopia_backend {
    server 127.0.0.1:8000;
    server 127.0.0.1:8001;
    server 127.0.0.1:8002;
}

server {
    location /api/ {
        proxy_pass http://vibeutopia_backend;
    }
}
```

> **注意**：多实例部署时需确保 WebSocket 连接的会话亲和性（sticky session）。

#### MySQL 读写分离

```bash
# 主库（写）
MYSQL_HOST=master.mysql.internal

# 从库（读）
# 需要修改应用代码支持读写分离
```

### ChromaDB 分片

当 ChromaDB 数据量增大时：

1. **按 Agent ID 分片**：不同 Agent 的记忆存储在不同 ChromaDB 实例
2. **按时间分片**：历史记忆归档到冷存储
3. **独立 ChromaDB 服务**：使用 ChromaDB Server 模式替代嵌入式模式

## LLM API 配额管理

### 多 Key 轮换策略

系统支持每个厂商配置多个 API Key，自动轮换：

```
# .env 配置示例（逗号分隔多个 Key）
DEEPSEEK_API_KEY=key1,key2,key3
```

**轮换逻辑：**
1. 优先使用第一个 Key
2. 当前 Key 配额耗尽 → 自动切换下一个
3. 同厂商全部耗尽 → 切换其他厂商
4. 所有厂商不可用 → 返回错误

### 配额监控

```bash
# 检查 Key 池状态
curl http://localhost:8000/api/v3/model-status
```

### 配额优化建议

1. **合理分配 Key**：不同 Key 分配给不同任务类型
2. **设置冷却时间**：`MODEL_COOLDOWN_SECONDS=300`，避免频繁切换
3. **混合使用厂商**：避免单一厂商依赖
4. **本地模型补充**：配置 Ollama/vLLM 作为本地备份

### 成本控制

| 策略 | 说明 |
|------|------|
| 快速分析用小模型 | `quick` 模式使用轻量模型 |
| 缓存分析结果 | 相同内容不重复调用 LLM |
| 批量分析优化 | 合并请求减少 API 调用次数 |
| 本地模型优先 | GPU 可用时优先使用本地模型 |

## 故障排查

### 常见错误和解决方案

#### 1. 后端启动失败

| 错误信息 | 原因 | 解决方案 |
|----------|------|----------|
| `ModuleNotFoundError` | 依赖未安装 | `pip install -r requirements.txt` |
| `Address already in use` | 端口被占用 | 更换端口或终止占用进程 |
| `Permission denied` | 权限不足 | 检查文件/目录权限 |

#### 2. 数据库连接失败

| 错误信息 | 原因 | 解决方案 |
|----------|------|----------|
| `Can't connect to MySQL` | MySQL 未启动 | `docker compose start mysql` |
| `Access denied` | 密码错误 | 检查 `.env` 中的密码配置 |
| `Too many connections` | 连接池耗尽 | 增加 `pool_size` 或减少并发 |

#### 3. LLM 调用失败

| 错误信息 | 原因 | 解决方案 |
|----------|------|----------|
| `API key invalid` | Key 无效 | 检查 `.env` 中的 Key 配置 |
| `Rate limit exceeded` | 请求频率过高 | 配置多 Key 或降低并发 |
| `Timeout` | 网络或服务问题 | 增加 `LLM_TIMEOUT` 值 |
| `Quota exhausted` | 配额耗尽 | 切换到其他厂商 Key |

#### 4. Neo4j 不可用

| 错误信息 | 原因 | 解决方案 |
|----------|------|----------|
| `Connection refused` | Neo4j 未启动 | `docker compose start neo4j` |
| `Auth failed` | 密码错误 | 检查 `.env` 中的 Neo4j 配置 |
| `Driver not installed` | neo4j 包未安装 | `pip install neo4j` |

> **重要**：Neo4j 不可用时系统自动降级到关系型数据库模式，核心功能不受影响。

#### 5. ChromaDB 异常

| 错误信息 | 原因 | 解决方案 |
|----------|------|----------|
| `Index corrupted` | 索引损坏 | 删除 `data/chroma_memories` 后重启 |
| `Disk full` | 磁盘空间不足 | 清理磁盘或迁移数据 |
| `Memory error` | 内存不足 | 增加内存或减少缓存 |

#### 6. 分析任务卡住

**排查步骤：**

1. 检查任务状态：`GET /api/v1/review/{task_id}/progress`
2. 检查 LLM 连通性：`GET /api/v3/llm-test`
3. 检查后端日志中的错误信息
4. 检查 API Key 配额是否耗尽

## 安全加固

### API Key 管理

1. **不要将 Key 提交到版本控制**
   - `.env` 文件已在 `.gitignore` 中
   - 使用 `.env.example` 作为模板

2. **定期轮换 Key**
   - 建议每 90 天更换一次 API Key
   - 使用多 Key 配置实现无缝切换

3. **最小权限原则**
   - 每个 Key 只申请必要的权限
   - 不同环境使用不同的 Key

### 网络安全

1. **后端不直接暴露**
   - 使用 Nginx 作为反向代理
   - 后端只监听 `127.0.0.1`

2. **CORS 配置**
   - 生产环境应限制 `allow_origins`
   - 避免使用 `*` 通配符

3. **防火墙规则**
   - 只开放 80/443 端口
   - 数据库端口不对外暴露

### 数据安全

1. **数据库加密**
   - MySQL 启用 SSL 连接
   - 敏感字段加密存储

2. **传输加密**
   - 全站 HTTPS
   - WebSocket 使用 WSS

3. **日志脱敏**
   - 不记录 API Key
   - 不记录用户原始内容
   - 不记录分析结果中的敏感信息

## 版本升级指南

### 升级前准备

1. **完整备份**
   ```bash
   # 执行所有备份脚本
   bash scripts/backup_mysql.sh
   bash scripts/backup_chroma.sh
   bash scripts/backup_neo4j.sh
   bash scripts/backup_config.sh
   ```

2. **记录当前版本**
   ```bash
   git log -1 --oneline
   pip freeze > requirements_old.txt
   ```

### 升级步骤

```bash
# 1. 停止服务
docker compose down
# 或
systemctl stop vibeutopia

# 2. 拉取新代码
git pull origin main

# 3. 更新依赖
pip install -r requirements.txt

# 4. 检查配置变更
diff .env.example .env

# 5. 数据库迁移（如有）
python -m backend.migrations.xxx

# 6. 启动服务
docker compose up -d
# 或
systemctl start vibeutopia

# 7. 验证服务
curl http://localhost:8000/api/v1/models
```

### 回滚

```bash
# 1. 停止服务
docker compose down

# 2. 回退代码
git checkout <previous-version-tag>

# 3. 恢复依赖
pip install -r requirements_old.txt

# 4. 恢复数据库
gunzip -c /backup/mysql/vibeutopia_YYYYMMDD.sql.gz | docker exec -i vibeutopia-mysql mysql -u vibe_user -pvibe_password vibeutopia

# 5. 启动服务
docker compose up -d
```
