## 3. 是否必须用 Linux？

### 直接回答：**不需要！两台 Windows 电脑都可以跑出项目最终最好的效果。**

| 误解 | 事实 |
|------|------|
| "vLLM 只支持 Linux" | WSL2 / Docker / 社区构建均可解决，且 Ollama 完全替代 |
| "CUDA 在 Windows 上性能差" | Windows 与 Linux CUDA 性能差距 < 5% |
| "大模型必须 Linux" | Ollama Windows 版原生支持 CUDA，RTX 4090D 跑 Qwen3.6-35B-A3B 无压力 |

**只有以下场景才需要原生 Linux：** 多 GPU 训练、生产环境部署、vLLM 多卡推理。你的场景是单卡推理 + API 混合，完全不需要。

## 4. 项目模型需求拆解

### 4.1 按任务类型拆解

| 任务类型 | 说明 | 模型需求 | 优先级 |
|---------|------|---------|--------|
| **文本理解与风险评估** | 11维风控评估、文案分析 | 强中文理解 + 推理 | 🔴 最高 |
| **Agent 仿真** | Persona 模拟、社交行为生成 | 强中文生成 + 角色扮演 | 🔴 最高 |
| **人生故事生成** | Agent 背景故事构建 | 长文本生成 + 创意 | 🟡 高 |
| **画面理解** | 视频帧风险检测、场景分析 | 视觉多模态 | 🟡 高 |
| **OCR 识别** | 视频字幕/贴图/水印文字 | 视觉 + 文字识别 | 🟠 中 |
| **音频转写** | 语音识别、说话人分离 | 音频模型 | 🟠 中 |
| **知识图谱构建** | 实体抽取、关系推理 | NER + 推理 | 🟠 中 |
| **情感分析** | 音频/文本情感判断 | 分类模型 | 🟢 低 |
| **向量嵌入** | Memory Stream 语义检索 | Embedding 模型 | 🟢 低 |

### 4.2 核心问题：项目是否需要多模型协同？

**是的，VibeUtopia 必须多模型协同。** 原因如下：

| 原因 | 说明 |
|------|------|
| **任务类型差异大** | 文本推理、视觉理解、音频转写是三种完全不同的能力，没有任何单一模型能同时做到最优 |
| **模态不同** | 纯文本模型不能看图，视觉模型做文本推理不如专用文本模型，音频需要专用模型 |
| **成本效率** | 用 560B 的 Omni 模型做简单 JSON 提取是大炮打蚊子，用 9B 模型做风险评估又力不从心 |
| **VRAM 限制** | 即使 24GB 也无法同时加载文本 + 视觉 + 音频三个大模型 |

### 4.3 顺序加载：A 任务完成后再跑 B 任务

**完全可以！而且这正是推荐的做法。** 你的思路非常正确：

```
处理一个视频的完整流程：

Phase 1: 文本分析（加载文本模型）
  ├── 风险评估 → Qwen3.6-35B-A3B / DeepSeek-V4-Flash
  ├── Agent 仿真 → Qwen3.6-35B-A3B
  └── 人生故事生成 → Qwen3.6-35B-A3B

Phase 2: 视觉分析（卸载文本模型，加载视觉模型）
  ├── 画面理解 → Qwen3-VL-32B / LongCat-Omni
  └── OCR 识别 → Qwen3-VL-32B / Qwen-VL-Plus

Phase 3: 音频分析（卸载视觉模型，加载音频模型）
  ├── 语音转写 → faster-whisper-large-v3
  └── 情感分析 → 基于转写文本的 LLM 分析

Phase 4: 跨模态融合（重新加载文本模型）
  └── 跨模态冲突检测 → Qwen3.6-35B-A3B
```

**这种方式的优势：**
- 每个阶段都能使用该任务类型下最优的模型
- 不需要同时加载多个模型，VRAM 完全够用
- 最终结果质量最高（因为每个任务都用了最好的模型）
- 唯一代价是模型切换时间（~5-15秒/次），但你明确表示不在乎时间

## 6. 多模型顺序加载策略（核心）

### 6.1 为什么顺序加载是最优策略？

| 方案 | 优势 | 劣势 | 效果 |
|------|------|------|------|
| 同时加载多模型 | 速度快 | VRAM 不够，只能用小模型 | ⭐⭐⭐ |
| **顺序加载（推荐）** | 每个任务用最优模型 | 切换有延迟（5-15秒） | ⭐⭐⭐⭐⭐ |
| 全 API | 零配置 | 成本高，依赖网络 | ⭐⭐⭐⭐⭐ |

**你说"不考虑时间损耗，最后的结果好就行"——顺序加载正是为此设计的。**

### 6.2 Ollama 顺序加载机制

Ollama 天然支持顺序加载，核心命令：

```bash
# 加载模型（自动卸载之前的模型释放 VRAM）
ollama run qwen3.6:35b-a3b    # 加载文本模型

# 手动卸载当前模型
ollama stop qwen3.6:35b-a3b

# 加载下一个模型
ollama run qwen3-vl:32b       # 加载视觉模型

# 查看当前 VRAM 中的模型
ollama ps
```

**Ollama 的 VRAM 管理行为：**
- 新模型请求时，如果 VRAM 不足，Ollama 自动卸载旧模型
- `OLLAMA_KEEP_ALIVE` 控制模型在 VRAM 中的驻留时间（默认 5 分钟）
- 设置 `OLLAMA_KEEP_ALIVE=0` 可让模型用完立即释放

### 6.3 项目 VRAMManager 集成

项目已有 `VRAMManager`（[vram_manager.py](file:///d:/project/VibeUtopia/src/backend/services/vram_manager.py)），支持：
- 按优先级加载/卸载模型
- LRU 淘汰策略
- 自动释放低优先级模型

**顺序加载策略与 VRAMManager 的配合：**

```python
# 伪代码：处理一个完整的风控任务
async def process_video_sequential(video_path):
    # Phase 1: 文本分析（加载文本模型）
    vram_manager.unload_all()
    vram_manager.load_model("qwen3.6-35b-a3b")  # 24GB: 用35B; 12GB: 用9B

    text_risk = await analyze_text_risk(text)
    agent_reactions = await simulate_agents(text)
    life_stories = await generate_life_stories()

    # Phase 2: 视觉分析（卸载文本，加载视觉模型）
    vram_manager.unload_model("qwen3.6-35b-a3b")
    vram_manager.load_model("qwen3-vl-32b")      # 24GB: 用32B; 12GB: 用8B

    visual_risks = await analyze_frames(frames)
    ocr_results = await extract_text_from_frames(frames)

    # Phase 3: 音频分析（卸载视觉，加载音频模型）
    vram_manager.unload_model("qwen3-vl-32b")
    # faster-whisper 独立进程，不通过 Ollama

    audio_transcript = await transcribe_audio(audio_path)
    audio_sentiment = await analyze_sentiment(audio_transcript)

    # Phase 4: 跨模态融合（重新加载文本模型）
    vram_manager.unload_all()
    vram_manager.load_model("qwen3.6-35b-a3b")

    cross_modal = await detect_cross_modal_conflicts(
        text_risk, visual_risks, audio_sentiment
    )

    return combine_results(text_risk, visual_risks, audio_sentiment, cross_modal)
```

### 7.1 方案 A：顺序加载 + API 辅助（推荐 ⭐⭐⭐⭐⭐）

| **常驻** | Embedding | **bge-m3** | - | ~2GB |

**VRAM 分时复用：**

```
Phase 1 (文本阶段):          Phase 2 (视觉阶段):        Phase 3 (音频阶段):
┌──────────────────────┐    ┌──────────────────────┐   ┌──────────────────────┐
│ Qwen3.6-9B   ~9.5GB │    │ Qwen3.5-VL-8B  ~6GB │   │ faster-whisper ~1.5GB│

└──────────────────────┘    └──────────────────────┘   └──────────────────────┘
```

**月成本：** ¥100-300（API 仅在需要时调用）

**优势：** 零 API 成本，完全离线可用

## 8. 台式机方案（24GB VRAM）

### 8.1 方案 A：顺序加载 + 大模型（推荐 ⭐⭐⭐⭐⭐）

**核心理念：24GB VRAM 可以跑 35B MoE 模型，这是质的飞跃。每个阶段都用该任务类型下最大的模型。**

| 阶段 | 任务 | 本地模型 | API 备选 | VRAM |
|------|------|---------|---------|------|
| **Phase 1** | 文本推理 | **Qwen3.6-35B-A3B (Q4_K_M)** | DeepSeek-V4-Flash | ~21GB |
| **Phase 2** | 视觉理解 | **Qwen3-VL-32B (Q4)** | LongCat-Omni | ~19.8GB |
| **Phase 3** | 音频转写 | **faster-whisper-large-v3** | Paraformer API | ~3GB |
| **Phase 4** | 全模态融合 | **Nemotron-3-Nano-Omni (Q4)** | - | ~20GB |
| **常驻** | Embedding | **bge-m3** | - | ~2GB |

**VRAM 分时复用：**

```
Phase 1 (文本阶段):          Phase 2 (视觉阶段):        Phase 3 (音频阶段):
┌──────────────────────┐    ┌──────────────────────┐   ┌──────────────────────┐

```

**关键优势：Qwen3.6-35B-A3B vs Qwen3.6-9B**

| 对比项 | Qwen3.6-9B (笔记本) | Qwen3.6-35B-A3B (台式机) |
|--------|--------------------|-------------------------|
| 参数量 | 9B Dense | 35B MoE (3B 激活) |
| SWE-bench | ~65 | **73.4** |
| 中文理解 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 推理速度 | ~80-105 tok/s | ~80-101 tok/s (激活参数少) |
| 风险评估准确率 | 基准 | **+10-15%** |

**月成本：** ¥0-100（几乎全本地，API 仅做 fallback）

### 8.2 方案 B：全模态本地（Nemotron-3-Nano-Omni 为主）

**核心理念：用 Nemotron-3-Nano-Omni 一个模型覆盖所有模态，简化架构。**

| 阶段 | 任务 | 模型 | VRAM |
|------|------|------|------|
| **Phase 1-4** | 文本+视觉+音频+融合 | **Nemotron-3-Nano-Omni (Q4)** | ~20GB |
| **常驻** | Embedding | **bge-m3** | ~2GB |

**优势：** 一个模型处理所有模态，无需切换
**劣势：** 中文能力不如 Qwen 系列；MoE 模型在某些任务上不如专用模型

### 8.3 方案 C：Dense 大模型（Qwen3.6-27B）

**核心理念：用 27B Dense 模型替代 35B MoE，Dense 模型在部分任务上更稳定。**

| 阶段 | 任务 | 模型 | VRAM |
|------|------|------|------|
| **Phase 1** | 文本推理 | **Qwen3.6-27B (Q4_K_M)** | ~17GB |
| **Phase 2** | 视觉理解 | **Qwen3-VL-32B (Q4)** | ~19.8GB |
| **Phase 3** | 音频转写 | **faster-whisper-large-v3** | ~3GB |
| **常驻** | Embedding | **bge-m3** | ~2GB |

**优势：** Dense 模型推理更稳定，Ollama 兼容性更好
**劣势：** 27B Dense 推理速度比 35B MoE 慢（每 token 激活 27B vs 3B）

## 9. 双机协作方案

### 9.1 方案：台式机跑本地大模型 + 笔记本跑前端/轻量任务

**核心理念：两台电脑分工协作，台式机作为"模型服务器"，笔记本作为"交互终端"。**

```
┌─────────────────────────────┐     ┌─────────────────────────────┐
│      台式机 (RTX 4090D)      │     │     笔记本 (RTX 5070 Ti)     │
│      24GB VRAM / 128GB RAM  │     │     12GB VRAM / 32GB RAM    │
├─────────────────────────────┤     ├─────────────────────────────┤
│                             │     │                             │
│  Ollama 服务 (模型服务器)    │     │  FastAPI 后端               │
│  ┌───────────────────────┐  │     │  ┌───────────────────────┐  │
│  │ Qwen3.6-35B-A3B      │  │     │  │ 路由请求到台式机       │  │
│  │ Qwen3-VL-32B         │◄─┼─────┼─►│ 本地跑 bge-m3         │  │
│  │ Nemotron-3-Nano-Omni │  │ LAN │  │ 本地跑 Qwen3.6-9B     │  │
│  │ faster-whisper-large  │  │     │  │ 前端 Vue3             │  │
│  └───────────────────────┘  │     │  └───────────────────────┘  │
│                             │     │                             │
│  OLLAMA_HOST=0.0.0.0:11434 │     │  OLLAMA_BASE_URL=           │
│                             │     │  http://<台式机IP>:11434/v1 │
└─────────────────────────────┘     └─────────────────────────────┘
```

**配置方法：**

台式机（模型服务器）：
```bash
# 设置 Ollama 监听所有网络接口
set OLLAMA_HOST=0.0.0.0:11434
ollama serve
```

笔记本（客户端）：
```env
# .env 配置指向台式机
OLLAMA_BASE_URL=http://192.168.x.x:11434/v1
```

**双机协作的任务分配：**

| 任务 | 运行位置 | 模型 | 原因 |
|------|---------|------|------|
| 文本推理（大模型） | 台式机 | Qwen3.6-35B-A3B | 需要 24GB VRAM |
| 视觉理解 | 台式机 | Qwen3-VL-32B | 需要 24GB VRAM |
| 音频转写 | 台式机 | faster-whisper-large-v3 | 128GB RAM 更快 |
| 文本推理（轻量） | 笔记本 | Qwen3.6-9B | 快速响应，不占台式机资源 |
| Embedding | 笔记本 | bge-m3 | 常驻，低 VRAM |
| 前端 | 笔记本 | Vue3 | 交互体验 |
| API 调用 | 笔记本 | DeepSeek-V4-Flash 等 | 网络请求无差别 |

### 9.2 独立运行模式

两台电脑也可以独立运行，互不依赖：

| 场景 | 使用设备 | 方案 |
|------|---------|------|
| 在家深度分析 | 台式机 | 24GB 全本地大模型方案 |
| 外出移动办公 | 笔记本 | 12GB 顺序加载 + API 方案 |
| 最高质量需求 | 双机协作 | 台式机跑大模型 + 笔记本跑前端 |

## 11. 降级方案与影响评估

### 11.1 两台电脑的降级路径

| 降级场景 | 笔记本 (12GB) | 台式机 (24GB) | 影响评估 |
|---------|--------------|--------------|---------|
| 无 API Key | 本地 Qwen3.5-VL-8B + whisper | 本地 Qwen3-VL-32B + whisper-large | 台式机几乎无影响 |
| VRAM 不足 | Qwen3.6-9B Q6→Q4 | Qwen3.6-35B→27B Q4 | 质量损失 < 5% |
| 无 Docker | SQLite + Neo4j 本地 | SQLite + Neo4j 本地 | 并发下降，功能不变 |
| 网络断开 | 纯本地顺序加载 | 纯本地顺序加载 | 台式机几乎无影响 |
| 台式机不可用 | 全 API 或笔记本本地 | - | 质量下降一个档次 |

### 11.2 Windows 上不需要降级

**两台 Windows 电脑均不需要任何功能降级。** 所有核心功能均可正常使用：
- ✅ 文本风控（本地 + API）
- ✅ 视觉风控（本地大模型 + API）
- ✅ 音频风控（本地 + API）
- ✅ Agent 仿真（本地大模型）
- ✅ 知识图谱（Neo4j via Docker）
- ✅ Memory Stream（ChromaDB 本地）
- ✅ 多模型顺序加载（Ollama + VRAMManager）

### 关键决策理由

| 决策 | 理由 |
|------|------|
| **顺序加载而非同时加载** | 你不在乎时间，在乎结果。顺序加载让每个任务都用最优模型 |
| **台式机用 35B MoE 而非 27B Dense** | 35B-A3B 每次仅激活 3B 参数，速度与 9B 相当，但质量远超 |
| **笔记本用 9B 而非勉强 14B** | 14B Q2/Q3 量化质量损失大，9B Q6 近无损，综合效果更好 |
| **Qwen3-VL-32B 做视觉** | 24GB 刚好能跑 Q4，效果远超 8B，是 24GB VRAM 的最佳视觉选择 |
| **Nemotron-3-Nano-Omni 做融合** | 原生支持文+图+音+视频，跨模态分析一次完成 |
| **bge-m3 常驻** | Memory Stream 检索频繁，常驻避免反复加载 |
| **Ollama 而非 vLLM** | Windows 原生支持 + `ollama stop` 完美适配顺序加载 |
